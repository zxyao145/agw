# Agw Server Deployment

Agw production releases run as one ASP.NET Core process. The Server hosts the API, WebSocket endpoints, setup pages, and the statically exported Web UI. Node.js is required only while building the release.

## Data directory

Portable releases store mutable data in the current user's `agw` directory:

- Windows: `%USERPROFILE%\agw`
- macOS and Linux: `~/agw`
- Container: `/data`

Set `AGW_DATA_DIR` to override the default. Back up `server-state.json`, `database/`, `skills/`, and `keys/` together. Logs and temporary files do not need to be restored.

## Project workspaces

`Project.Workspace` is not copied into the Agw data directory. It must name a directory visible to the Server process; the file API, Git commands, Claude Code, and Codex all use that same working tree.

For network storage, mount it through the operating system or container platform before starting Agw, then configure the mount path as the Workspace. The mount must provide the locking, rename, and consistency semantics required by Git. Containers need an explicit bind mount, and every execution replica must see the same path. Agw does not provide an application-level SFTP backend.

The file-system resolver caches a Project after its first use. Restart the Server after changing an already-resolved Workspace.

## Portable Server

Start the extracted package with `agw-server serve` (`agw-server.exe serve` on Windows). Running without the `serve` argument remains supported. It listens on `http://127.0.0.1:30816` unless `ASPNETCORE_URLS` is set.

Reset a forgotten administrator password while the Server is stopped:

```bash
agw-server auth reset-password
```

## Container

Build and run the single-process image:

```bash
PUBLISH_MODE=docker APP_VERSION=0.1.0 IMAGE_NAME=agw:0.1.0 ./publish.sh
docker load -i artifacts/publish/docker/agw-server-0.1.0-linux-arm64.tar
docker run --rm -p 127.0.0.1:30816:8080 -v agw-data:/data agw:0.1.0-arm64
```

The default build writes loadable Linux amd64 and arm64 image archives. The image contains the statically exported `@agw/web` application and the ASP.NET Core Server in one process. Set `DOCKER_PLATFORMS` to restrict the local build to one platform.

To publish a multi-platform manifest, log in to the registry and provide every desired tag through `IMAGE_TAGS`:

```bash
PUBLISH_MODE=docker \
APP_VERSION=0.1.0 \
IMAGE_NAME=ghcr.io/zxyao145/agw:0.1.0 \
IMAGE_TAGS="ghcr.io/zxyao145/agw:0.1.0 ghcr.io/zxyao145/agw:latest" \
DOCKER_PUSH=true \
./publish.sh
```

`IMAGE_TAGS` accepts spaces, commas, or newlines. `APP_VERSION` is also written into the Server assembly and OCI image metadata.

The first startup prints a one-time remote Setup Code. Direct `localhost` setup does not require the code. Setup asks for a deployment mode and structured database settings; users never need to compose a connection string.

- **Standalone** uses the in-process execution runtime and supports either a Server-visible SQLite database path or PostgreSQL.
- **Cluster** uses distributed durable execution, requires PostgreSQL, and stores PostgreSQL as the distributed lock provider. Restart the first Server after setup before adding replicas.

For unattended container initialization, provide a `Setup` configuration section through environment variables or the platform's configuration provider. The smallest Standalone SQLite configuration is:

```yaml
services:
  agw:
    environment:
      Setup__AdminPassword: "${AGW_ADMIN_PASSWORD}"
```

The default SQLite file is `/data/database/agw.db`. A PostgreSQL Cluster deployment uses:

```yaml
services:
  agw:
    environment:
      Setup__DeploymentMode: Cluster
      Setup__Provider: Postgres
      Setup__PostgresHost: postgres
      Setup__PostgresPort: 5432
      Setup__PostgresDatabase: agw
      Setup__PostgresUsername: agw
      Setup__PostgresPassword: "${AGW_POSTGRES_PASSWORD}"
      Setup__AdminPassword: "${AGW_ADMIN_PASSWORD}"
```

When `/data/server-state.json` is absent, startup validates the configuration and runs database migration, seeding, password hashing, and the atomic state write before accepting traffic. If initialization fails, the container exits and no completed state is written. Once the state file exists, `Setup__*` values are ignored so restarts cannot replace the administrator password or runtime setup choices. Keep `/data` persistent and inject both passwords from Docker or orchestrator Secrets rather than committing them to Compose or `appsettings*.json`.

Configuration-driven Cluster setup starts with the distributed runtime immediately and does not need the additional restart required by the browser flow. Run one Agw replica for the initial bootstrap, wait for the readiness check to pass, then scale out.

## Automated releases

`.github/workflows/release.yml` builds the Docker image and all Desktop installers after every push to `main`, on stable `vX.Y.Z` tags, and when manually dispatched. Main and default manual runs upload temporary Actions artifacts only.

A stable tag publishes `linux/amd64` and `linux/arm64` to `ghcr.io/<owner>/<repository>` using the exact, minor, major, `latest`, and commit SHA tags. It also creates a GitHub Release containing the Desktop installers. A manual run publishes only when `publish` is enabled and a `release_tag` in `vX.Y.Z` format is provided; if the tag does not exist, it is created at the selected workflow ref.

## Domain access

Terminate TLS with Caddy or Nginx on the host and proxy to `127.0.0.1:30816`. Keep the Agw HTTP port bound to loopback, preserve the original Host, and forward scheme/client headers. Set `AllowedHosts` to the public hostname. Loopback proxies are trusted by default; add any other proxy IP through `ReverseProxy__TrustedProxies`. The Compose example uses a fixed Docker gateway and trusts only that gateway. See `deploy/Caddyfile.example`, `deploy/nginx.conf.example`, and `deploy/compose.yaml`.

SignalR uses the `access_token` query parameter for authenticated browser WebSocket handshakes. Configure reverse-proxy access logs to record the path without its query string; the Nginx example uses `$uri` instead of `$request_uri` or `$request` for this reason.

Agw v1 supports a dedicated domain root such as `https://agw.example.com/`. Deploying below a path such as `/agw` and direct certificate management by Agw are not supported. SQLite is limited to Standalone mode. Cluster mode requires all replicas to use the same PostgreSQL database and PostgreSQL advisory locks; setup configures the lock provider to reuse the application database connection.

## Upgrading existing installations

This version adds the `api_token` table through matching SQLite and PostgreSQL migrations. The Server applies the selected provider's pending migration during setup. Stop the old Server and back up its files before upgrading.

- SQLite: copy the old database to `agw/database/agw.db`, or enter its absolute Server path during setup.
- PostgreSQL: enter the existing host, port, database, username, and password during setup.
- Skills: copy the old `wwwroot/skills` contents to `agw/skills`.
- Authentication: the old `X-API-Key` is not migrated. Create a new administrator password and named API Tokens.
