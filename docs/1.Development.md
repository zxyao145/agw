# Build And Development Commands

## Backend

### Commands

Run from the repo root:

```bash
dotnet restore Agw.slnx
dotnet tool restore
dotnet build Agw.slnx
dotnet run --project src/server/Agw.Standalone.Host
dotnet watch --project src/server/Agw.Standalone.Host
dotnet test Agw.slnx
dotnet csharpier format
```

Notes:

- Deployment settings use the standard configuration chain, above built-in defaults. The Setup page only creates the administrator password; unattended first run uses `Setup__AdminPassword`. See the [Deployment Guide](4.Deployment.md) for examples and split Host requirements.

- The Standalone development Host launches on `http://localhost:30816` by default via `src/server/Agw.Standalone.Host/Properties/launchSettings.json`; Data Plane uses `http://localhost:30817` when launched separately.
- `DistributedLock:Provider` may be `inmemory` or `postgres`. Leave it null or omit it to derive the lock from the current database provider; an empty PostgreSQL lock connection string reuses the current database connection string.
- Do not add or apply EF Core migrations automatically. Generate matching migrations for both providers when the model changes:

```bash
dotnet ef migrations add <MigrationName> \
  -p src/server/Agw.Migrations.Sqlite \
  -s src/server/Agw.Standalone.Host \
  -- --provider sqlite

dotnet ef migrations add <MigrationName> \
  -p src/server/Agw.Migrations.Postgres \
  -s src/server/Agw.Standalone.Host \
  -- --provider postgres

dotnet ef database update \
  --connection "<sqlite-connection-string>" \
  -p src/server/Agw.Migrations.Sqlite \
  -s src/server/Agw.Standalone.Host \
  -- --provider sqlite

dotnet ef database update \
  --connection "<postgres-connection-string>" \
  -p src/server/Agw.Migrations.Postgres \
  -s src/server/Agw.Standalone.Host \
  -- --provider postgres
```

### Tests

```bash
# Run all tests
dotnet test Agw.slnx

# Run a focused project or test
dotnet test tests/Agw.Files.Tests
dotnet test tests/Agw.Files.Tests --filter "FullyQualifiedName~MethodName"
```

Test projects use xUnit v3.

Server builds audit transitive NuGet dependencies and reject High/Critical advisories. CI also treats audit retrieval failures as errors.

The PostgreSQL fencing and overlapping event-batch tests require `AGW_TEST_POSTGRES_CONNECTION_STRING` pointing to an isolated PostgreSQL instance with permission to create temporary databases. CI runs them with PostgreSQL 18 and verifies their TRX results so missing or skipped tests cannot pass the gate:

```bash
AGW_TEST_POSTGRES_CONNECTION_STRING="Host=localhost;Database=postgres;Username=agw_test;Password=agw_test;Pooling=false" \
  dotnet test tests/Agw.Agents.Tests -c Release \
  --filter "FullyQualifiedName~PostgresExecutionFencingTests|FullyQualifiedName~PostgresBatch_ConcurrentOverlappingBatches" \
  --logger trx --results-directory TestResults/Postgres
python3 .github/scripts/verify-postgres-tests.py TestResults/Postgres
```

### Backend Exceptions

Backend code uses a centralized exception model in `src/server/Agw.Shared/Exceptions/`:

- `AgwException` carries `int Code`, `HttpStatusCode StatusCode`, and the exception message. `StatusCode` defaults to `HttpStatusCode.BadRequest` when a constructor does not receive one.
- `ErrorCode` is `public record ErrorCode(int Code, string Message, HttpStatusCode StatusCode)`.
- `ErrorCodes.cs` is the only catalog for reusable backend error codes.

When adding or changing backend exception handling:

1. Use `throw new AgwException(ErrorCodes.SomeCode)` for expected validation, domain, application, scheduler, tool, or runtime failures.
2. Use `throw new AgwException(ErrorCodes.SomeCode, "...")` when the message needs runtime context. Keep the `ErrorCodes` catalog message generic enough to reuse.
3. Do not add new explicit `throw new ArgumentException`, `InvalidOperationException`, `NotSupportedException`, `HttpRequestException`, `FileNotFoundException`, `DirectoryNotFoundException`, `UriFormatException`, or protocol-specific exceptions in `src/server` for expected application failures.
4. Reuse existing `ErrorCodes` entries when possible. Add a new entry only when the failure is meaningfully distinct for API clients, logs, or tests.
5. New `ErrorCode.Code` values must be 7 digits. The first 3 digits must equal the HTTP status code, and the final 4 digits increment within that status group. Examples: `400_0001`, `404_0003`, `500_0010`.
6. Do not renumber existing error codes. Append the next value in the matching status-code group.
7. Keep boundary-specific protocol behavior at the boundary. A2A internals throw `AgwException`; `AgwA2AJsonRpcProcessor` maps those to A2A JSON-RPC errors. Controllers that need custom HTTP responses should catch `AgwException`.
8. Update tests to assert `AgwException.Code` and `StatusCode` instead of framework exception types. Run `dotnet test tests/Agw.Shared.Tests/Agw.Shared.Tests.csproj` after changing exception rules or error codes.



### Code Formatting

```bash
dotnet csharpier format
```

CSharpier is provided as a local dotnet tool (see `.config/dotnet-tools.json`); run `dotnet tool restore` once after cloning. Limit formatting to the files changed by the task to avoid unrelated diffs.



## Web, Desktop, and Mobile Clients

`@agw/web`, `@agw/desktop`, `@agw/mobile`, and the `@agw/*` packages under `src/clients/packages/` share the pnpm Workspace rooted at `src/clients` and use Turborepo for task orchestration. Run all pnpm commands below from `src/clients`; one install covers the complete workspace:

```bash
pnpm install
```

The common workspace-wide commands are:

```bash
pnpm build
pnpm typecheck
pnpm lint
pnpm test
pnpm fmt
pnpm fmt:check
```

`pnpm typecheck` runs `tsc` in every package and application; `pnpm test` depends on it, and applications bundle package sources directly. Shared library versions are defined once in the `catalog` section of `pnpm-workspace.yaml`. Turborepo uses its local task cache only; remote caching is disabled. Use a root script when one is available. For a package-specific Web task, use `pnpm exec turbo run <task> --filter=@agw/web`.

### Web Development

```bash
pnpm dev:web
```

The Web Next.js dev server runs on `http://localhost:3001`. `src/clients/web/next.config.ts` rewrites `/api/*` and `/openapi/*` to `BACKEND_API_BASE_URL`, then `NEXT_PUBLIC_API_BASE_URL`, then `http://localhost:30816` unless static export mode is enabled.

Run browser behavior tests with `pnpm --filter @agw/web exec playwright install chromium` followed by `pnpm --filter @agw/web test:e2e`. Playwright starts an isolated Web server on `127.0.0.1:3101` with `AGW_E2E=1` and the `.next-e2e` build directory; it does not reuse the Web or Desktop development server. The tests stub API responses and cover login retry and Agentflow save behavior in desktop and mobile browser viewports, without requiring a backend. Web CI runs this suite. `pnpm test` also runs API compile-time contract checks; missing required request parameters must fail compilation.

Business-domain code lives under `src/clients/packages/`; `src/clients/web/src/app/` is limited to browser routes, layouts, global CSS, and shell composition. Web and Desktop do not import, locate, build, or consume artifacts from each other. Desktop owns its Next.js route shell and Electron adapter under `src/clients/desktop/renderer/`, with internal bridge contracts under `desktop/src/shared/contracts/`. Both applications compose business modules from root `packages/*`; execution status and aggregation belong to `@agw/chat-runtime`, while `@agw/chat` owns the shared DOM renderer.

Regenerate `src/clients/packages/api/src/openapi.d.ts` after backend contract changes with:

```bash
pnpm gen:api
```

### Desktop Development

Start Desktop and its independent Renderer together:

```bash
pnpm dev:desktop
```

The Desktop renderer listens on `http://localhost:3000` during development. It does not require `pnpm dev:web`.

### Desktop Packaging

Build either installer flavor from `src/clients`:

```bash
AGW_PACKAGE_FLAVOR=client pnpm make:desktop
AGW_PACKAGE_FLAVOR=full pnpm make:desktop
```

Optionally pass an architecture through to Electron Forge:

```bash
pnpm make:desktop -- --arch=x64
```

## Mobile Client

The Expo Router app is the `@agw/mobile` package under `src/clients/mobile` and participates in the pnpm/Turborepo workspace rooted at `src/clients`. Run `pnpm dev:mobile`, `pnpm android:mobile`, or `pnpm ios:mobile` from `src/clients`; native `android/` and `ios/` directories are generated through Expo CNG and are not hand-maintained.


### OIDC verification

The Auth tests use a controlled OIDC provider and per-test SQLite databases by default. They cover independent Server/Desktop PKCE, protocol failures, ownership, registration concurrency, one-time handoff, transactional rollback, and fresh/upgrade migrations.

```bash
dotnet test tests/Agw.Auth.Tests/Agw.Auth.Tests.csproj
dotnet test tests/Agw.Architecture.Tests/Agw.Architecture.Tests.csproj
```

To run the same Auth tests against an isolated PostgreSQL test server, set `AGW_TEST_OIDC_POSTGRES` to its admin connection string. The test role must be able to create databases. Each fixture creates a uniquely named `agw_oidc_test_*` database and drops only that database during cleanup. Never point this test setting at a production server.

After backend contract changes, export the development OpenAPI document to `src/clients/packages/api/openapi.json` and run `pnpm gen:api` from `src/clients`. Desktop's main-process login/proof/storage tests run with `pnpm --filter @agw/desktop test`.
