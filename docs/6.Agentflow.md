# Agentflow Graphs, Editor, and Chat Attribution

Agentflows are persisted, Input-rooted directed workflow graphs compiled into Microsoft Agent Framework workflows. They support branching, fan-in, orchestration blocks, human approval, and controlled cycles; they are not restricted to DAGs.

This document is the current source of truth for graph invariants, editor state, and Agentflow message attribution. The general execution lifecycle remains documented in [Agent Execution Flow](ws-flow.md) and the [Execution subsystem README](../src/server/Agw.Agents/Execution/README.md).

## Graph contract

Every persisted graph must satisfy these invariants:

- It has exactly one `Input` node with `nodeId = "input"` and no incoming edges.
- Every runtime-visible node is reachable from `Input`. Agent participants owned only by an orchestration block are validated as block members rather than top-level graph nodes.
- Node IDs and edge IDs are unique, and every edge references existing nodes.
- Agent references, block membership, Output summary configuration, edge predicates, routing strategies, and cycle safety are validated before persistence.
- An Agent node with an empty name is normalized to the referenced Agent name. An explicitly configured node name is retained.

Supported node kinds are:

| Kind | Runtime behavior |
| --- | --- |
| `Input` | Passes the user's turn input into the graph. |
| `Agent` | Executes a referenced Agent with node-scoped instructions and history. |
| `WorkflowAsAgent` | Executes a nested Agentflow as an Agent. |
| `PromptAdapter` | Applies node instructions to the current messages. |
| `ClearMessages` | Continues with an empty upstream message payload; it does not clear downstream Agent session history. |
| `HumanGate` | Pauses for approval and exposes the approved reply to outgoing edge predicates. Rejection stops the workflow. |
| `CheckpointMarker` | Creates an explicit superstep boundary and associates its configured name with the full MAF checkpoint created at the end of that superstep. |
| `ConcurrentBlock`, `HandoffBlock`, `GroupChatBlock`, `MagenticBlock` | Execute their configured Agent or nested-Agentflow participants as one graph node. |
| `Output` | Emits graph output and may append a configured result summary. |

## Edge routing

A source node uses one outbound routing strategy, excluding edges that participate in a target-side Fan-in Barrier:

| Edge kind | Semantics |
| --- | --- |
| `Direct` | Each edge is evaluated independently. An edge without a predicate always routes. |
| `FanOut` | Routes to every target whose predicate matches; edges without predicates always match. |
| `SwitchCase` | Evaluated in ascending `ConfigJson.switchCaseOrder`; the first matching case routes. Every case requires a predicate and a unique non-negative order. |
| `SwitchDefault` | Optional fallback for a Switch source. A source may have at most one default, and it has no predicate. |
| `FanInBarrier` | Grouped by target. The target runs after every distinct source in the group has arrived. |

Do not mix Direct, Fan Out, and Switch edges from the same source. A Switch requires at least one case; its default is optional.

`ConditionJson` must be a non-empty JSON object when present. Supported properties are `always`, `contains`, `notContains`, `equals`, `author`, `role`, and `minMessages`. String predicates inspect the current message set; predicates leaving a HumanGate inspect the latest approved human reply.

## Controlled cycles

Cycles are allowed only when every cyclic strongly connected component has at least one `SwitchCase` or `SwitchDefault` edge that exits the component. This makes the graph's termination path explicit and rejects unconditional closed loops.

A Fan-in Barrier inside a cycle may receive an out-of-cycle source only from the one-shot `Input` node. For that supported pattern, the runtime stores the initial Input messages in workflow checkpoint state, waits for every in-cycle barrier source on each iteration, emits the combined messages, and then clears only the per-iteration inputs. Any other out-of-cycle barrier source is rejected during validation.

The client runs the same cycle checks before save, but `AgentflowDomainService` remains the authoritative validation boundary.

## Checkpoints

Agentflow execution follows the [Microsoft Agent Framework checkpoint model](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints). Every run is started with a dedicated `CheckpointManager`, so MAF captures executor state, pending messages, pending requests and responses, and shared state at the end of every superstep. A `CheckpointMarker` does not serialize a partial message snapshot; it creates a named graph boundary whose executor ID is associated with the checkpoint emitted for that superstep.

In-process execution uses an isolated in-memory manager for the lifetime of one run. Distributed execution uses the JSON checkpoint store and persists the latest HumanGate boundary to PostgreSQL, then rebuilds the same workflow topology and calls `ResumeStreamingAsync`. Executor identities therefore remain stable across rebuilds; Agent nodes use their persisted node IDs.

## Editor session state

The visual editor creates one private Zustand `5.0.15` vanilla store for each open dialog. The store is internal to `@agw/agents`; it is not a module-level singleton, is not exported publicly, does not use React Flow's internal store, and is discarded when the dialog closes. React Query continues to own server data and API mutations, so a query refresh does not replace an open editor document.

The store owns the editable document, canvas scope, selection, save status, baseline fingerprint, and `past`/`present`/`future` history:

- History retains at most 100 steps. A new edit after Undo clears Redo history.
- Node and edge mutations, block membership changes, routing changes, deletion with related edges, and automatic layout are atomic history steps.
- A node drag is grouped from drag start through drag stop. Continuous text editing is grouped until blur.
- React Flow measurement updates, temporary selection, and viewport changes do not enter history or mark the document dirty.
- Undo and Redo remove selection or block scope references that no longer exist.
- `Cmd/Ctrl+Z`, `Cmd/Ctrl+Shift+Z`, and Windows `Ctrl+Y` operate on graph history outside editable controls. Inputs and textareas keep native text Undo behavior.

Dirty state is calculated by comparing a normalized, saveable document fingerprint with the initial baseline. A new editor containing its default Input node starts clean. Cancel, Close, and Escape close immediately when clean and require an explicit Discard confirmation when dirty. A successful save marks the current document clean and closes the dialog; a failed save preserves dirty state and history. Drafts are not persisted across dialog sessions or page reloads.

## Execution history and Chat labels

Each Agent node uses a history scope derived from the Agentflow ID and node ID, which keeps repeated uses of the same Agent isolated by workflow node. Response messages, streaming updates, and separately persisted Tool state snapshots receive `additionalProperties.nodeName` before they leave the node or enter history.

Message attribution follows these rules:

- Existing `nodeName` metadata wins, so orchestration blocks and nested Agentflows preserve the innermost executing node name.
- The original message author is not replaced. When a persisted response has no author, history also records `additionalProperties.agentName` as the Agent identity fallback.
- User request messages and conversation preludes are not tagged as Agentflow responses.
- Chat displays `nodeName / author` when both are available and falls back to the Agent identity when the node name is absent.
- Live output and newly persisted history therefore render consistently after reload. Existing records created without this metadata are not backfilled.
