# 对话历史与事件持久化

Agw 分别配置对话历史和分布式事件的写入节奏。配置来自 appsettings、环境变量和 Host 参数，遵循 ASP.NET Core 标准优先级；修改后重启生效。多副本部署应保持执行节点配置一致。

## Host 模板配置

```json
{
  "ConversationHistory": {
    "Mode": "Interval",
    "FlushIntervalSeconds": 10,
    "MaxBufferedBytes": 16777216
  },
  "Execution": {
    "Distributed": {
      "EventStream": {
        "WriteIntervalMilliseconds": 250,
        "WriteBatchSize": 100
      }
    }
  }
}
```

| 历史模式 | 常规提交时机 |
| --- | --- |
| `Interval` | 从首条待写消息开始计时，Host 模板为 10 秒后提交；没有后续消息也会触发 |
| `TurnEnd` | 回合结束时提交 |
| `Immediate` | 历史 Provider 每次追加时立即提交 |

`ConversationHistoryOptions` 的代码兜底仍为 5 秒；只有省略 `FlushIntervalSeconds` 配置时才使用它。以下行为按部署的有效间隔执行。

两种延迟模式均在缓冲达到 `MaxBufferedBytes` 时提前提交。该值按消息与元数据的序列化 UTF-8 字节数估算，默认每个执行作用域 16 MiB；单次追加可能跨过阈值，达到阈值的调用会等待提交。它不是整个进程的堆内存上限。

普通模型 Agent 在读取本次调用的历史之后立即将原始输入入队，并捕获流式回复增量；因此长回复尚未完成时，`Interval` 也能按周期保存。每条回复的中间快照复用同一记录 ID，完成后原位更新为完整消息；中间快照仅用于历史展示，不参与模型上下文或跨目标交接。聚合发生在读取/刷新边界，避免每个 token 都重新序列化整篇回复。

后续刷新只重新聚合和序列化变化的消息尾部，已提交且未变化的前序消息不会再次进入写入批次。读取和失败重试复用待写快照，只有提交成功才清理；完成回调会更新各条消息的完整状态。单条仍在增长的消息继续按完整 JSON 快照保存，因此长文本的单次更新成本仍随文本长度增加。

Web/Desktop 的可见 Chat 在运行期间每 5 秒刷新会话列表，结束或卸载时停止；列表展示的是数据库已提交数量，因此还可能包含一次查询周期的延迟。

独立调用历史追加接口而没有执行作用域时，仍立即提交。外部 SDK 的聚合窗口继续存在：例如 Codex 先按 20 条更新或 1 秒聚合，再交给历史 Provider；Claude Code 只提交 SDK 已完成的消息，未完成 partial Assistant 的处理保持原状。

原始输入的暂存、去重和流式响应状态统一由 `EfCoreChatHistoryProvider` 管理。Claude/Pi 适配器直接委托给它；Agents 模块通过 Contracts 接口调用请求生命周期能力，不依赖 EF 实现。SDK 会话之间的待写请求独立保存，结束时在 SDK 释放回调完成后统一清理。

## 恢复边界与读取

- 普通 Agent、外部 Agent 和 Agentflow 的执行入口建立历史作用域；Agentflow 节点保留各自的历史范围并复用外层缓冲。
- 模型读取包含当前作用域尚未提交的消息，因此工具循环和后续模型调用仍有完整上下文。历史 REST 查询仅返回已提交内容。
- 正常结束、取消、异常和消费方提前释放枚举器时，会尝试保存剩余历史；最终刷新使用独立的 30 秒超时。正常完成标记在历史提交后发送。
- 保存 SDK session state、记录检查点及其历史截止序号之前，会先刷新历史并阻止并发追加越过该边界；durable 分段在进入可恢复等待状态前完成提交。因此 `TurnEnd` 也可能在这些恢复边界提前保存。
- 会话重置或删除后，旧代次缓冲不能写回；执行权失效后停止提交对应缓冲。定时数据库故障保留有效作用域中的待写批次，之后重试；同一批次重用记录 ID，避免丢失提交确认导致重复记录。

初始化会话/任务、执行状态、用量、检查点及恢复所需的状态继续使用各自的持久化边界。

## 分布式事件

普通输出达到写入间隔或批量条数时提交，默认分别为 250 毫秒、100 条。数据库变慢时，写入器对生产方施加背压。PostgreSQL 每批通过 EF 提交，继续使用现有加密；Redis 使用有序 pipeline，并每批刷新 TTL。

事件在入队时只序列化一次，批次保存不可变 JSON，两个存储实现直接使用该快照。Redis 追加被服务端拒绝时，通过查询实际 stream ID 确认重复或缺失位置，不依赖错误文案；无法确认已写入的其他存储故障继续进入不可用降级。

事件仍保留逐条位置和 cursor，相同位置的首次提交内容保持不变。正常分段结束时先排空普通事件，再保存等待/结束状态和发布控制消息；状态轮询也会重新读取最后一批事件，避免提前结束订阅。作废分段的尚未提交事件丢弃，事件流不可用时执行继续依靠持久状态机完成。

分布式前端只有在事件提交后才能读到对应输出，因此显示延迟包含批量窗口和原有读取轮询间隔。事件写入策略独立于历史模式，不随 `TurnEnd` 等到整轮结束。

## 环境变量与回退

仅在回合结束及必要边界保存历史：

```bash
ConversationHistory__Mode=TurnEnd
```

显式配置与 Host 模板相同的 10 秒间隔：

```bash
ConversationHistory__Mode=Interval
ConversationHistory__FlushIntervalSeconds=10
```

恢复 Provider 逐次写入和分布式事件逐条写入：

```bash
ConversationHistory__Mode=Immediate
Execution__Distributed__EventStream__WriteIntervalMilliseconds=0
```

历史间隔和缓冲阈值必须为正；历史间隔还必须符合 .NET Timer 的范围。事件写入间隔可为 0，批量条数必须为正。无效配置在启动时拒绝。

调整写入节奏本身不需要数据库迁移，也不改变 REST/SignalR 格式。突发进程退出或掉电可能丢失尚未提交的历史；`TurnEnd` 下可能涉及本轮自上个必要提交边界以来的记录。正常关闭会尝试刷新，但不提供断电持久性保证。分布式未完成执行仍沿用已有的至少一次分段恢复语义。

优化主要减少事务提交、锁竞争和磁盘同步次数。每条消息/事件的存储格式保持兼容，累计存储量仍取决于记录总量及清理策略。

## 验证

相关测试使用可控时钟检查计时、容量阈值和结束刷新，使用事务计数验证同批提交，并覆盖模型读取、并行节点范围、重试、代次失效、事件游标及终态竞争。真实 PostgreSQL 测试沿用 `AGW_TEST_POSTGRES_CONNECTION_STRING`，要求指定可创建临时数据库的隔离实例；测试仅创建并删除自身的临时数据库。
