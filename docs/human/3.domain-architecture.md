# Domain Architecture

## Core Model

本项目采用 **贫血领域模型（Anemic Domain Model）**，将领域状态与领域行为显式分离：

```text
Application
└── ApplicationService
    └── Use Case Orchestration

Domain
├── AggregateRoot / Entity / ValueObject
│   └── State
│
├── Behavior
│   └── Single-Aggregate Behavior
│
└── DomainService
    └── Domain Rules Beyond a Single Aggregate Boundary

Infrastructure
└── IO / Persistence / External Systems
```

核心职责：

```text
Entity             = State
Behavior           = Single-Aggregate Behavior
DomainService      = Cross-Aggregate / External Domain Rules
ApplicationService = Orchestration
Infrastructure     = Technical IO
```

## Behavior

`Behavior` 承担**单个 Aggregate Boundary 内部的领域行为和状态转换**。

例如：

```csharp
public sealed class OrderBehavior
{
    private readonly Order _order;

    public OrderBehavior(Order order)
    {
        _order = order;
    }

    public void Submit()
    {
        if (_order.Status != OrderStatus.Pending)
            throw new DomainException(
                "The order cannot be submitted in its current state.");

        if (_order.Items.Count == 0)
            throw new DomainException(
                "An empty order cannot be submitted.");

        _order.Status = OrderStatus.Submitted;
    }

    public void Cancel()
    {
        if (_order.Status == OrderStatus.Completed)
            throw new DomainException(
                "A completed order cannot be cancelled.");

        if (_order.Status == OrderStatus.Cancelled)
            return;

        _order.Status = OrderStatus.Cancelled;
    }
}
```

判断标准：

> 如果完成一项业务行为所需要的全部领域状态都位于同一个 Aggregate Boundary 内，则该行为属于 Behavior。

例如：

```text
OrderBehavior.Submit()
OrderBehavior.Cancel()
OrderBehavior.AddItem()

UserBehavior.Disable()
UserBehavior.ChangeEmail()

SubscriptionBehavior.Pause()
SubscriptionBehavior.Resume()
```

Behavior 可以读取和修改整个 Aggregate 内部的状态，但不应该为了完成规则而查询其他 Aggregate。

## DomainService

`DomainService` 承担**无法仅依靠单个 Aggregate 自身状态完成的领域规则**。

典型情况包括：

- 规则需要查询其他 Aggregate 的状态；
- 规则需要判断整个 Aggregate 集合中的事实；
- 规则涉及唯一性等跨 Aggregate 约束；
- 规则本身跨越多个 Aggregate Boundary；
- 该领域行为无法自然地由某个单一 Aggregate 的 Behavior 完成。

例如创建用户时存在两条领域规则：

```text
Email 必须唯一
UserName 必须唯一
```

这些规则明确属于 User Domain，但一个新创建的 `User` 无法知道其他 User 使用了哪些 Email 和 UserName。

因此由 `UserDomainService` 负责：

```csharp
public sealed class UserDomainService
{
    private readonly IUserRepository _users;

    public UserDomainService(IUserRepository users)
    {
        _users = users;
    }

    public async Task<User> CreateAsync(
        string userName,
        Email email,
        CancellationToken cancellationToken = default)
    {
        if (await _users.ExistsByEmailAsync(
                email,
                cancellationToken))
        {
            throw new DomainException(
                $"Email '{email}' is already in use.");
        }

        if (await _users.ExistsByUserNameAsync(
                userName,
                cancellationToken))
        {
            throw new DomainException(
                $"UserName '{userName}' is already in use.");
        }

        return new User(
            UserId.New(),
            userName,
            email);
    }
}
```

这里虽然业务操作仍然是：

```text
Create User
```

但判断规则需要知道：

```text
                  UserDomainService
                         │
                         ▼
                  IUserRepository
                    /         \
                   ▼           ▼
          Email 是否存在   UserName 是否存在
                    \         /
                     ▼       ▼
                    Domain Rule
                         │
                         ▼
                       User
```

因此属于 DomainService，而不是 `UserBehavior`。

### Repository in DomainService

DomainService 可以依赖 **Domain Repository abstraction** 获取完成领域规则所必需的领域事实。

例如：

```csharp
public interface IUserRepository
{
    Task<bool> ExistsByEmailAsync(
        Email email,
        CancellationToken cancellationToken = default);

    Task<bool> ExistsByUserNameAsync(
        string userName,
        CancellationToken cancellationToken = default);
}
```

Domain 层只依赖：

```text
IUserRepository
```

而不知道其技术实现：

```text
EF Core
PostgreSQL
SQL
Redis
HTTP
```

实际依赖关系：

```text
Domain
│
├── UserDomainService
│       │
│       ▼
│   IUserRepository
│
└───────────────────────┐
                        │ implements
                        ▼
                Infrastructure
                UserRepository
                        │
                        ▼
                   PostgreSQL
```

因此：

> DomainService 可以为了执行领域规则获取必要的领域事实，但不应该包含数据库、HTTP、Redis 等具体技术实现。

## Behavior vs DomainService

两者最核心的区别是 **Aggregate Boundary**：

```text
                   Domain Rule
                        │
                        ▼
          单个 Aggregate 能否完成？
                  /             \
                Yes              No
                 │                │
                 ▼                ▼
             Behavior       DomainService
```

例如：

| Rule | Owner |
|---|---|
| Pending Order 才能 Submit | `OrderBehavior` |
| 空 Order 不能 Submit | `OrderBehavior` |
| Completed Order 不能 Cancel | `OrderBehavior` |
| User 当前状态是否允许 Disable | `UserBehavior` |
| Email 是否已经被其他 User 使用 | `UserDomainService` |
| UserName 是否已经被其他 User 使用 | `UserDomainService` |
| Customer 是否满足某 Order 的信用要求 | DomainService |
| Promotion 是否适用于 Customer + Order | DomainService |

因此可以概括为：

```text
Behavior
    = Rules within one Aggregate Boundary

DomainService
    = Rules beyond one Aggregate Boundary
```

注意：

> “跨 Aggregate”并不意味着方法参数中必须同时出现两个 Aggregate。

例如：

```csharp
UserDomainService.CreateAsync(userName, email)
```

虽然没有：

```csharp
CreateAsync(User user1, User user2)
```

但唯一性规则实际上涉及：

```text
New User
   +
Existing Users
```

因此其规则已经超出了单个 User Aggregate 的边界。

## ApplicationService

ApplicationService 负责 **Use Case Orchestration**。

例如注册用户：

```csharp
public sealed class RegisterUserHandler
{
    private readonly UserDomainService _userDomainService;
    private readonly IUserRepository _users;
    private readonly IUnitOfWork _unitOfWork;

    public async Task<UserId> Handle(
        RegisterUserCommand command,
        CancellationToken cancellationToken)
    {
        var user = await _userDomainService.CreateAsync(
            command.UserName,
            new Email(command.Email),
            cancellationToken);

        await _users.AddAsync(
            user,
            cancellationToken);

        await _unitOfWork.SaveChangesAsync(
            cancellationToken);

        return user.Id;
    }
}
```

Application 负责：

```text
RegisterUserHandler
        │
        ├── 调用 UserDomainService
        │          │
        │          ├── 校验 Email 唯一性
        │          ├── 校验 UserName 唯一性
        │          └── 创建 User
        │
        ├── Repository.Add(User)
        │
        └── SaveChanges
```

这里需要特别区分：

```text
UserDomainService
    “创建 User 必须满足什么业务规则？”

RegisterUserHandler
    “完成注册用户这个 Use Case 需要执行哪些步骤？”
```

前者是 **Domain Rule**，后者是 **Orchestration**。

## Decision Guide

遇到业务逻辑时按照下面的方式判断：

```text
                      Logic
                        │
                        ▼
                 是业务规则吗？
                   /        \
                 No          Yes
                 │            │
                 ▼            ▼
          Application /   单个 Aggregate
          Infrastructure   能否完成？
                          /         \
                        Yes          No
                         │            │
                         ▼            ▼
                     Behavior    DomainService
```

典型调用关系：

```text
                    ApplicationService
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
          Behavior                DomainService
              │                         │
              ▼                         ▼
       Single Aggregate       Multiple Aggregates /
                              Aggregate-wide Facts
```

## Architecture Rules

### Rule 1 — Entity owns State

Aggregate Root / Entity / Value Object 主要表达领域状态。

```text
Entity = State
```

### Rule 2 — Behavior owns Aggregate Behavior

单个 Aggregate Boundary 内的业务行为和状态转换由 Behavior 负责。

```text
Order → OrderBehavior
User → UserBehavior
```

### Rule 3 — DomainService owns Rules Beyond an Aggregate

无法仅依靠一个 Aggregate 自身状态完成的领域规则由 DomainService 负责。

包括：

```text
跨 Aggregate Rule
Aggregate-wide Rule
Uniqueness Rule
需要查询其他 Aggregate 才能完成的 Rule
```

DomainService 可以依赖 Repository abstraction 获取必要的领域事实。

### Rule 4 — Application owns Orchestration

ApplicationService 负责：

```text
Load
Coordinate
Call Domain
Persist
Publish
```

但不应该实现 Domain Rule。

### Rule 5 — Infrastructure owns Technical IO

数据库、HTTP、MQ、Redis 等具体技术实现属于 Infrastructure。

Domain 可以依赖 Repository abstraction，但不能依赖具体的：

```text
DbContext
SQL
HttpClient
Redis Client
MQ Client
```

### Rule 6 — Do Not Force Domain Logic

简单 CRUD 没有 Domain Rule 时，可以直接：

```text
API
 ↓
Application
 ↓
Repository
```

不需要人为制造 Behavior 或 DomainService。

## Summary

整个架构最终可以用四句话描述：

> **Entity stores state.**

> **Behavior implements business behavior within a single Aggregate boundary.**

> **DomainService implements business rules that go beyond a single Aggregate boundary.**

> **ApplicationService orchestrates the use case.**

即：

```text
Entity             = State
Behavior           = Single-Aggregate Behavior
DomainService      = Beyond-Aggregate Domain Rules
ApplicationService = Orchestration
```

典型调用关系：

```text
                    API
                     │
                     ▼
              ApplicationService
                     │
          ┌──────────┴──────────┐
          │                     │
          ▼                     ▼
      Behavior             DomainService
          │                     │
          ▼                     ▼
   One Aggregate       Cross-Aggregate Facts
          │                     │
          └──────────┬──────────┘
                     ▼
                  Entity
                     │
                     ▼
                Persistence
```

这套架构的目标不是实现传统的 Rich Domain Model，而是在保持贫血 Entity 简单、易于持久化和理解的同时，避免业务规则泄漏到 ApplicationService 中：

```text
State         → Entity
Local Rule    → Behavior
Global Rule   → DomainService
Workflow      → ApplicationService
Technical IO  → Infrastructure
```
