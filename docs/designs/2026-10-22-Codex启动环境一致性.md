# Codex 启动环境一致性修复方案

## 背景

[issue #198](https://github.com/zxyao145/agw/issues/198) 报告：macOS 上的 AGW Desktop 0.4.3 使用 CodexSdk 10.0.2 启动 npm 版 Codex CLI 0.162.1 时，进程退出码为 `127`，标准错误为 `env: node: No such file or directory`。问题中的父进程 `PATH` 为 `/usr/bin:/bin:/usr/sbin:/sbin`，Node 位于 `/opt/homebrew/bin`。

分析基准为 issue 指定的 SDK commit `4fa8f47e31434abf360e0c157b070951382cc426`。截至本次检查，AGW 工作区的 `src/server/Directory.Packages.props` 指定 `CodexSdk.MAF 10.0.1`，其恢复结果包含 `CodexSdk 10.0.1`。这两个版本需要分别记录；本方案的 SDK 修改针对 issue 指定的 `FindAsync` 实现。

本次使用安装在仓库 `.scratch/issue-198/cli` 内的真实 `@openai/codex@0.162.1` 发布包完成了以下验证：

- npm 启动器的第一行是 `#!/usr/bin/env node`。
- 子进程仅使用系统目录组成的 `PATH` 时，退出码为 `127`，输出与 issue 一致。
- 同一启动器的子进程 `PATH` 加入实际 Node 目录后，退出码为 `0`，输出 `codex-cli 0.162.1`。
- 自动化复现文件为 `.scratch/issue-198/codex-launcher-path.test.mjs`，两个断言均通过。这个实验验证 npm 启动器对执行环境的依赖。

当前机器的 `/opt/homebrew/bin/codex` 指向 Homebrew 安装的原生 CLI 0.163.0。复现实验使用上述独立安装的 npm 发布包。

## 设计目标

### 功能目标

1. 通过 login shell 的 `PATH` 找到 Codex 后，将该搜索路径传给实际 Codex 子进程，使 Node 和后续工具能够按相同目录顺序查找。
2. `CodexOptions.Env` 同时参与程序查找和子进程启动。
3. 支持 AGW 注入执行环境后形成的非空 `CodexOptions.Env`。
4. 保留显式程序路径、正常 PATH 查找、Windows 环境变量大小写、取消和超时行为。

### 技术目标

本次执行使用独立的环境快照。调用方字典和宿主进程环境保持原值。程序继续通过 `ProcessStartInfo` 和 `ArgumentList` 直接启动，保留现有标准流、进程取消和退出码处理。

## 详细设计

### 从进程启动条件推导修复位置

一次进程启动由程序入口、参数、工作目录和环境共同决定。对于 npm 版 Codex，操作系统根据 shebang 启动 `/usr/bin/env`；随后 `env` 使用子进程的 `PATH` 查找 `node`。Codex 文件的绝对路径只确定程序入口。

设宿主提供的环境为 `E0`，其中的搜索路径为 `P0`；login shell 读取启动配置后提供的搜索路径为 `P1`。issue 中的执行过程是：

1. 在 `P0` 中查找 Codex。
2. login shell 提供 `P1`，SDK 在其中找到 npm 启动器。
3. SDK 使用该启动器的绝对路径创建子进程。
4. 子进程收到 `E0`，`env node` 继续使用 `P0`。

根本约束是：**查找阶段为选定程序引入的 PATH，必须成为该次执行的 PATH。** 同时，查找阶段必须使用调用方选定的基础环境。

[CommandUtil.cs](https://github.com/zxyao145/codex-sdk-csharp/blob/4fa8f47e31434abf360e0c157b070951382cc426/src/CodexSdk/Utils/CommandUtil.cs) 已经取得 shell 的 PATH 和工作目录，但 `CommandInfo` 的返回值只保留命令路径、来源和错误信息。[CodexExec.cs](https://github.com/zxyao145/codex-sdk-csharp/blob/4fa8f47e31434abf360e0c157b070951382cc426/src/CodexSdk/CodexExec.cs) 在查找时使用默认环境，随后才将 `_envOverride` 应用于子进程。

程序查找和实际进程创建都属于 CodexSdk，修复由 SDK 完成。AGW 通过依赖更新接收修复，使 Desktop 管理的 Server、Standalone Host 和 Data Plane 使用相同的启动规则。当前 Desktop 的 macOS Server 由 `DaemonManager.installLaunchAgent` 注册给 launchd 管理。

### 一次执行的环境处理顺序

在 `CodexExec` 内按以下顺序准备进程：

1. 复制基础环境：`_envOverride` 非空时复制它，否则复制当前进程环境。Windows 使用不区分大小写的键比较，Unix 使用区分大小写的键比较。
2. 将该快照通过 `CommandLookupOptions.Environment` 传给 `CommandUtil.FindAsync`。
3. 查找成功后，如果结果携带 login shell 的搜索路径，将它设置为快照中的 `PATH`。
4. 创建 `ProcessStartInfo`，清空其默认环境，再完整复制上述快照。
5. 按现有语义添加 `CODEX_INTERNAL_ORIGINATOR_OVERRIDE`，并应用本次请求的 `CODEX_API_KEY`。
6. 设置现有参数和请求的工作目录，直接创建进程。

`ApplyEnvironment` 的现有职责需要配合该顺序调整：基础环境只建立一次，SDK 添加的变量在查找完成后应用。`args.ApiKey` 保持在最终 CLI 的环境中。

将现有进程准备部分提取为 `CodexExec.CreateProcessStartInfoAsync(CodexExecArgs args, CancellationToken cancellationToken)`，返回实际供 `RunAsync` 使用的 `ProcessStartInfo`。该内部方法同时提供真实进程启动的组件测试入口。

### CommandInfo 保留 login shell 的搜索路径

在现有内部类型 `CommandInfo` 中增加可选的 `SearchPath` 属性：

- `Source == CommandSource.LoginShell` 且找到命令时，返回查找实际使用的完整 PATH。
- `Source == CommandSource.Path` 或 `CommandSource.ExplicitPath` 时，该属性为 `null`，表示继续使用输入环境中的 PATH。
- 查找失败时保留现有错误信息，调用方在启动目标进程之前结束本次操作。

保持原有 record 构造参数顺序，使用新增属性承载这项信息。该类型继续保持 `internal`。

shell 返回的 PATH 保留目录顺序。每个非空相对目录按 shell 同时返回的工作目录转换成绝对路径，再将这一份结果用于查找和返回。空项继续遵循当前查找逻辑的忽略规则；显式的 `.` 按 shell 的工作目录解析。这样，即使 shell 启动配置改变了目录，Codex 仍可在请求指定的项目目录内启动，并获得含义明确的 PATH。

保留完整目录序列，覆盖 Codex 启动器与 Node 位于不同目录的安装方式。保持符号链接入口名称。环境传播仅采用本次查找取得的 PATH，其余变量来自基础环境快照。

### Env 和 CodexPathOverride 的行为

`Env` 的完整替换语义继续有效：提供 `Env` 后，SDK 以它作为唯一的基础环境来源；缺少的变量不会从宿主环境补入。调用方提供的字典保持原值。

具体查找规则如下：

1. 优先在这份环境的 PATH 中查找命令，命中后保持它的 PATH。
2. Unix 上未命中，且这份环境包含受支持的 `SHELL` 时，按照现有规则启动 login shell；辅助进程也使用这份环境。
3. login shell 查找成功后，采用其返回并规范化的 PATH。这个规则也适用于非空 `Env`，需要在 `CodexOptions.Env` 的说明中写明。
4. 空 `Env` 且未指定可用的显式程序路径时，报告未找到命令。

`CodexPathOverride` 继续指定程序入口。显式路径不存在时直接报告错误；显式路径存在时使用选定的基础环境执行。脚本解释器由该环境提供。该分支保持现有的显式路径查找规则。

Windows 保持 PATH、PATHEXT 和环境变量名称的现有平台规则。取消、三秒 shell 查询超时以及辅助进程清理继续沿用现有实现。查找和启动错误保留来源与原因，并结束本次执行。

### AGW 集成

`AgentRuntimeFactory.CreateCodexOptionsWithEnvironmentVariables` 会把已有 `CodexOptions.Env` 或宿主环境与执行环境合并，作为新的 `CodexOptions.Env` 传给 SDK。因此，SDK 的 shell 路径传播需要同时支持 `Env == null` 和非空 `Env`。

AGW 的实现步骤为：

- 保留现有环境组合逻辑及其字段传递。
- 将 `src/server/Directory.Packages.props` 中的 `CodexSdk.MAF` 更新到包含本方案修复的已发布版本。
- 检查恢复结果，确认传递依赖 `CodexSdk` 对应包含修复的版本和源码。
- 验证 `BuildCodexAIAgentOptions` 产生的环境能够保留 AGW 执行变量及用户提供的程序路径。

## 测试计划

### SDK 单元测试

- `FindAsync_LoginShellPath_ReturnsSearchPath`：命令仅存在于 shell 提供的 PATH，结果同时包含正确的程序路径、来源及搜索路径。
- `FindAsync_LoginShellRelativePath_ReturnsAbsoluteSearchPath`：真实 shell 切换目录，PATH 包含相对目录与空格；返回的目录顺序及绝对路径正确。
- `CreateProcessStartInfoAsync_EnvProvided_UsesProvidedEnvironmentForLookup`：宿主 PATH 与显式 Env.PATH 指向不同位置，选择显式 Env 中的真实 Codex 入口。
- `CreateProcessStartInfoAsync_EnvProvided_PreservesEnvironmentIsolation`：宿主独有变量不进入子进程，调用方字典保持原值；SDK 自有变量按现有优先级设置。
- `CreateProcessStartInfoAsync_LoginShellSelected_PreservesResolvedPath`：最终 ProcessStartInfo 包含 shell PATH，后续环境处理保持该值。
- `CreateProcessStartInfoAsync_ExplicitPath_UsesProvidedEnvironment`：使用真实 npm 入口和包含 Node 的环境，保持指定入口与环境。
- 继续覆盖空环境、缺失显式路径、正常 PATH 命中、Windows 大小写与 PATHEXT、shell 超时和调用方取消。
- 并行准备两个不同的执行环境，验证结果互相独立，宿主环境保持原值。

### 真实进程组件测试

使用固定版本的 npm Codex 发布包、真实 Node 和真实 zsh 或 bash。测试数据与 shell 启动配置放在项目内的测试目录；用子进程环境传入测试所需 PATH、HOME 和 shell 配置位置。

关键用例的条件为：

1. 基础 PATH 只有系统目录。
2. Codex 启动器与 Node 分别位于两个额外目录，两个目录均由测试 shell 的启动配置加入 PATH。
3. `CodexPathOverride` 为空，通过 login shell 查找 Codex。
4. SDK 的进程准备方法返回实际 `ProcessStartInfo`，测试将命令参数设为 `--version`，启动真实 Codex 进程。
5. 断言退出码为 `0`，标准输出为固定 CLI 版本；调用方和宿主的 PATH 保持原值。

分别以继承环境和 AGW 风格的完整 `Env` 执行上述用例。再覆盖 shell 工作目录与项目目录不同的场景。这个测试入口复用 `RunAsync` 的生产进程准备逻辑，版本查询覆盖本次故障涉及的 shebang、解释器查找和操作系统进程创建。

### AGW 回归与发布验收

- 环境组合测试覆盖：继承宿主环境、已有完整 Env、AGW 执行变量、保留 `CodexPathOverride`。
- 执行 AGW 构建及相关 Agents 测试，确认 NuGet 审计和编译通过。
- 相关集成与组件测试全部通过后，在 macOS 的常规 Desktop 使用方式下，通过真实 npm 版 Codex 完成一次最小请求及一次继续会话。
- 记录实际 SDK 与 CLI 版本、入口路径、查找来源、退出状态和会话结果；诊断信息仅记录需要的环境键名。

验收条件为：受限的宿主 PATH 下，SDK 能通过 login shell 找到并启动 npm Codex；AGW 的非空 Env 路径同样通过；相对 shell PATH、环境隔离和平台规则均有对应的测试结果。
