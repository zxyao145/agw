# Module Organization

Agw is a modular monolith. Backend modules are split by business domain and use lightweight layering where it helps:

```text
Api → Application → Domain ← Infrastructure
```

Dependencies point inward. Domain objects are intentionally anemic: they contain data only, while business behavior belongs in Application-layer services.

## Api

The Api layer adapts external protocols to application calls.

It contains:

- Controllers and route builders
- Request and response DTOs
- Protocol mapping, routing, and validation
- Boundary-specific authentication and error conversion

It must not contain business workflows, persistence logic, or provider-specific infrastructure.

Backend JSON controllers return `Bens.Results.ApiResult` envelopes. Protocol boundaries such as WebSockets, OAuth redirects, A2A, and static files may retain their protocol-specific formats.

## Application

The Application layer coordinates use cases and owns business behavior.

It contains:

- AppServices, RuntimeServices, and DomainServices
- Workflows and use-case coordination
- Repository and unit-of-work orchestration
- Application-facing adapter interfaces

It may depend on Domain data and inward-facing contracts, but not on Api controllers or client UI.

## Domain

The Domain layer contains framework-free entities and value objects only. Agw deliberately uses an anemic domain model.

It must not contain:

- Business workflows or behavior methods
- Database, HTTP, JSON, or UI code
- Framework dependencies
- Infrastructure implementations

Put behavior that reasons about domain data in an Application-layer service such as `AgentflowDomainService`.

## Infrastructure

The Infrastructure layer implements technical adapters required by Application code.

It contains:

- EF Core contexts, repository implementations, migrations, and interceptors
- Provider-specific database and distributed-lock adapters
- External API and transport implementations
- Encryption and other framework integrations

Infrastructure may implement inward-facing interfaces, but Domain must not depend on it.

## Typical Flow

```text
Controller
  → AppService / RuntimeService
  → DomainService
  → IRepository / IUnitOfWork
  → EF Core
```

Not every module needs a folder for every layer. Keep code in the owning business module, use the smallest structure that preserves the dependency direction, and place shared persistence entities in `Agw.Data`.

Cross-module calls use dedicated contract assemblies and Facade adapters:

```text
Caller → Agw.<Module>.Contracts → Facade Adapter → internal AppService / RuntimeService / IRepository
```

`Agw.Agents.Contracts`, `Agw.Projects.Contracts`, and `Agw.Jobs.Contracts` contain only cross-module interfaces and DTOs. They never reference their implementation projects. Runtime topology selection, persistence entities, EF queries, and application orchestration stay behind the Facade seam.

## Automated Architecture Guardrails

`tests/Agw.Architecture.Tests/BackendArchitectureTests.cs` enforces the backend boundaries:

- The exact server project-reference graph must match the allowed dependency matrix in that test.
- Source below a `Domain` folder must not reference EF Core or ASP.NET Core.
- A module must not reference a sibling module's `Application`, `Domain`, or `Infrastructure` namespace, including through fully qualified type names. Cross-module consumers use the sibling module's `Contracts` namespace or an explicitly allowlisted public module facade instead.
- Guarded module-root namespaces are reserved for files in `AllowedRootNamespaceFacadeFiles`; adding one is a public API review decision.
- A `*.Contracts` project may depend only on `Agw.Shared` or another `*.Contracts` project.
- Production modules may not reference a sibling Agents/Projects/Jobs AppService, RuntimeService, or owned entity repository directly.

Run `dotnet test tests/Agw.Architecture.Tests` after changing project references, namespaces, or module boundaries. An intentional project-graph change must update the matrix in the same change.
