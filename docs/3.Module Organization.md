# Module Organization

Agw is a modular monolith. Backend modules are split by business domain and use lightweight layering where it helps:

```text
Api → Application → Domain ← Infrastructure
```

Dependencies point inward. Domain objects are permanently anemic: they contain data only. Entity-bound business behavior lives in manually constructed `Domain/Behaviors/<Entity>Behavior` classes, while Application owns use-case orchestration.

## Api

The Api layer adapts external protocols to application calls.

It contains:

- Controllers and route builders
- Request and response DTOs
- Protocol mapping, routing, and validation
- Boundary-specific authentication and error conversion

It must not contain business workflows, persistence logic, or provider-specific infrastructure.

Backend JSON controllers return `Bens.Results.ApiResult` envelopes. Protocol boundaries such as WebSockets, OAuth redirects, A2A, and static files may retain their protocol-specific formats.

## Application

The Application layer coordinates use cases, loads external facts, and invokes domain Behaviors, Policies, and DomainServices.

It contains:

- AppServices and RuntimeServices
- Workflows and use-case coordination
- Loading complete data boundaries and external facts before constructing Behaviors
- Repository and unit-of-work orchestration
- Application-facing adapter interfaces

It may depend on Domain data and inward-facing contracts, but not on Api controllers or client UI.

## Domain

The Domain layer contains framework-free anemic data types, Behaviors, pure Policies, and genuine cross-boundary DomainServices. Agw deliberately and permanently rejects behavior-rich entities.

It must not contain:

- Business workflows or behavior methods on data types
- Database, HTTP, JSON, or UI code
- Framework dependencies
- Infrastructure implementations

## Behavior

Behavior that a rich model would place on an entity is externalized into a concrete `Domain/Behaviors/<Entity>Behavior` class. A Behavior is an entity-bound, short-lived wrapper rather than an IoC service.

```csharp
public sealed class AgentflowBehavior
{
    private readonly Agentflow _agentflow;

    public AgentflowBehavior(Agentflow agentflow)
    {
        ArgumentNullException.ThrowIfNull(agentflow);
        _agentflow = agentflow;
    }

    public AgentflowValidationResult ValidateAndNormalize(
        AgentflowBehaviorContext context,
        DateTimeOffset now,
        string actor
    )
    {
        // Validate and mutate _agentflow plus its owned Nodes and Edges.
    }
}
```

Application first loads the complete consistency boundary, then executes `new AgentflowBehavior(agentflow)`. Behavior may mutate the bound root and owned children, but it has no independent persisted state and cannot mutate foreign entities. External facts, time, and actor identity are method inputs.

Behavior is never registered with IoC, never cached or serialized, and never given Repository, DbContext, HTTP, filesystem, MAF/MCP, current-user, or Infrastructure dependencies. Do not define `I<Entity>Behavior` without two real Adapters and explicit architecture approval. Do not create a Behavior for simple CRUD that has no business invariants.

## Policy and DomainService

Domain component construction follows its actual lifetime:

- An entity-bound Behavior is always constructed manually because it wraps one loaded data root.
- A pure Domain Policy is constructed manually at its call site by default. IoC remains available only when a real composition need justifies it.
- A genuine DomainService may be managed by IoC when its rule spans multiple data boundaries. It must remain stateless and its constructor dependencies must be pure Domain components.

A single-root `XxxDomainService` is misplaced entity Behavior. An IoC-managed DomainService cannot capture Behavior instances or data roots and cannot depend on persistence, transport, current-user, clock, filesystem, MAF/MCP, Application, or Infrastructure services. Application passes data and external facts into the DomainService, receives a data-only decision, and applies that decision through the relevant Behaviors.

## Infrastructure

The Infrastructure layer implements technical adapters required by Application code.

It contains:

- EF Core contexts, repository implementations, migrations, and interceptors
- Provider-specific database and distributed-lock adapters
- External API and transport implementations
- Encryption and other framework integrations

Infrastructure may implement inward-facing interfaces, but Domain must not depend on it.

## Typical Flow

```text
Controller
  → AppService / RuntimeService
  → new XxxPolicy() / injected cross-boundary DomainService (when needed)
  → new XxxBehavior(completeData)
  → Behavior method
  → I<Module>DbContext / internal persistence adapter
  → EF Core
```

Not every module needs a folder for every layer. Keep code in the owning business module and use the smallest structure that preserves the dependency direction. Entities remain physically hosted in `Agw.Data` during the ownership migration, but their query and write ownership belongs to one business module.

Modules with persisted entities expose an `I<Module>DbContext` interface under `Application/Persistence`. These interfaces contain only the owner's `DbSet` values and `SaveChangesAsync`; they do not expose transactions, `DatabaseFacade`, or `ChangeTracker`. `AgwDbContext` is the single scoped adapter for all eight interfaces. Files, Setup, and A2A own no tables and therefore have no empty DbContext interface.

Cross-module calls use dedicated contract assemblies and Facade adapters:

```text
Caller → Agw.<Module>.Contracts → Facade Adapter → internal AppService / RuntimeService / IRepository
```

`Agw.Agents.Contracts`, `Agw.Projects.Contracts`, and `Agw.Jobs.Contracts` contain only cross-module interfaces and DTOs. They never reference their implementation projects. Runtime topology selection, persistence entities, EF queries, and application orchestration stay behind the Facade seam.

## Automated Architecture Guardrails

`tests/Agw.Architecture.Tests/BackendArchitectureTests.cs` enforces the backend boundaries:

- The exact server project-reference graph must match the allowed dependency matrix in that test.
- Source below a `Domain` folder must not reference EF Core or ASP.NET Core.
- A module must not reference a sibling module's `Application`, `Domain`, or `Infrastructure` namespace, including through fully qualified type names. Cross-module consumers use the sibling module's `Contracts` namespace or an explicitly allowlisted public module facade instead.
- Guarded module-root namespaces are reserved for files in `AllowedRootNamespaceFacadeFiles`; adding one is a public API review decision.
- A `*.Contracts` project may depend only on `Agw.Shared` or another `*.Contracts` project.
- Production modules may not reference a sibling Agents/Projects/Jobs AppService, RuntimeService, or owned entity repository directly.
- Every table entity must appear exactly once in the persistence ownership manifest, and every Module DbContext `DbSet` must match that manifest.
- A module may reference only its own Module DbContext interface. Contracts projects must not reference EF Core, Agw.Data, or any Module DbContext.
- Raw `DbContext`, `AgwDbContext`, and generic repository usage is protected by a decreasing baseline ratchet.
- Persisted/domain data types may not acquire new business methods; the existing exceptions are held in a decreasing allowlist.
- Entity-bound Behavior must live below `Domain/Behaviors`, remain framework-free, and be manually constructed.
- IoC registrations and `I<Entity>Behavior` interfaces are forbidden for Behavior classes.
- Existing entity-specific `DomainService` names are migration debt; the architecture guard forbids adding new single-root DomainServices while allowing genuine cross-boundary DomainServices.

Run `dotnet test tests/Agw.Architecture.Tests` after changing project references, namespaces, or module boundaries. An intentional project-graph change must update the matrix in the same change.
