# Domain Architecture

## Core Model

This project uses the **Anemic Domain Model**, explicitly separating domain state from domain behavior:

```text
Application
└── ApplicationService
    └── Use Case Orchestration

Domain
├── AggregateRoot / Entity / ValueObject
│   └── State
│
├── Behavior
│   └── Single-Aggregate Behavior
│
└── DomainService
    └── Domain Rules Beyond a Single Aggregate Boundary

Infrastructure
└── IO / Persistence / External Systems
```

Core responsibilities:

```text
Entity             = State
Behavior           = Single-Aggregate Behavior
DomainService      = Cross-Aggregate / External Domain Rules
ApplicationService = Orchestration
Infrastructure     = Technical IO
```

## Behavior

`Behavior` is responsible for **domain behavior and state transitions within a single Aggregate Boundary**.

For example:

```csharp
public sealed class OrderBehavior
{
    private readonly Order _order;

    public OrderBehavior(Order order)
    {
        _order = order;
    }

    public void Submit()
    {
        if (_order.Status != OrderStatus.Pending)
            throw new DomainException(
                "The order cannot be submitted in its current state.");

        if (_order.Items.Count == 0)
            throw new DomainException(
                "An empty order cannot be submitted.");

        _order.Status = OrderStatus.Submitted;
    }

    public void Cancel()
    {
        if (_order.Status == OrderStatus.Completed)
            throw new DomainException(
                "A completed order cannot be cancelled.");

        if (_order.Status == OrderStatus.Cancelled)
            return;

        _order.Status = OrderStatus.Cancelled;
    }
}
```

Decision criterion:

> If all domain state required to complete a business behavior is contained within the same Aggregate Boundary, that behavior belongs in `Behavior`.

For example:

```text
OrderBehavior.Submit()
OrderBehavior.Cancel()
OrderBehavior.AddItem()

UserBehavior.Disable()
UserBehavior.ChangeEmail()

SubscriptionBehavior.Pause()
SubscriptionBehavior.Resume()
```

`Behavior` can read and modify state throughout its Aggregate, but should not query other Aggregates to complete a rule.

## DomainService

`DomainService` is responsible for **domain rules that cannot be completed using only the state of a single Aggregate**.

Typical cases include:

- The rule requires querying the state of another Aggregate;
- The rule requires evaluating facts across a collection of Aggregates;
- The rule involves a cross-Aggregate constraint such as uniqueness;
- The rule itself spans multiple Aggregate Boundaries;
- The domain behavior cannot naturally be handled by the `Behavior` of a single Aggregate.

For example, user creation has two domain rules:

```text
Email must be unique
UserName must be unique
```

These rules clearly belong to the User domain, but a newly created `User` cannot know which email addresses and user names are used by other users.

Therefore, `UserDomainService` is responsible for enforcing them:

```csharp
public sealed class UserDomainService
{
    private readonly IUserRepository _users;

    public UserDomainService(IUserRepository users)
    {
        _users = users;
    }

    public async Task<User> CreateAsync(
        string userName,
        Email email,
        CancellationToken cancellationToken = default)
    {
        if (await _users.ExistsByEmailAsync(
                email,
                cancellationToken))
        {
            throw new DomainException(
                $"Email '{email}' is already in use.");
        }

        if (await _users.ExistsByUserNameAsync(
                userName,
                cancellationToken))
        {
            throw new DomainException(
                $"UserName '{userName}' is already in use.");
        }

        return new User(
            UserId.New(),
            userName,
            email);
    }
}
```

Although the business operation is still:

```text
Create User
```

the rule must determine:

```text
                  UserDomainService
                         │
                         ▼
                  IUserRepository
                    /         \
                   ▼           ▼
          Does the email exist?   Does the user name exist?
                    \         /
                     ▼       ▼
                    Domain Rule
                         │
                         ▼
                       User
```

Therefore, this belongs in a `DomainService`, not in `UserBehavior`.

### Repository in DomainService

`DomainService` can depend on a **Domain Repository abstraction** to obtain the domain facts required to enforce a domain rule.

For example:

```csharp
public interface IUserRepository
{
    Task<bool> ExistsByEmailAsync(
        Email email,
        CancellationToken cancellationToken = default);

    Task<bool> ExistsByUserNameAsync(
        string userName,
        CancellationToken cancellationToken = default);
}
```

The Domain layer depends only on:

```text
IUserRepository
```

and knows nothing about its technical implementation:

```text
EF Core
PostgreSQL
SQL
Redis
HTTP
```

Actual dependency relationship:

```text
Domain
│
├── UserDomainService
│       │
│       ▼
│   IUserRepository
│
└───────────────────────┐
                        │ implements
                        ▼
                Infrastructure
                UserRepository
                        │
                        ▼
                   PostgreSQL
```

Therefore:

> A `DomainService` can retrieve the domain facts needed to enforce a domain rule, but should not contain concrete technical implementations such as database, HTTP, or Redis code.

## Behavior vs DomainService

The key difference between the two is the **Aggregate Boundary**:

```text
                   Domain Rule
                        │
                        ▼
          Can a single Aggregate handle it?
                  /             \
                Yes              No
                 │                │
                 ▼                ▼
             Behavior       DomainService
```

For example:

| Rule | Owner |
|---|---|
| Only a Pending Order can be submitted | `OrderBehavior` |
| An empty Order cannot be submitted | `OrderBehavior` |
| A Completed Order cannot be cancelled | `OrderBehavior` |
| Whether the User can be disabled in its current state | `UserBehavior` |
| Whether the email is already used by another User | `UserDomainService` |
| Whether the user name is already used by another User | `UserDomainService` |
| Whether the Customer meets the credit requirements for an Order | DomainService |
| Whether the promotion applies to the Customer + Order | DomainService |

This can be summarized as:

```text
Behavior
    = Rules within one Aggregate Boundary

DomainService
    = Rules beyond one Aggregate Boundary
```

Note:

> “Cross-Aggregate” does not mean that the method parameters must include two Aggregates.

For example:

```csharp
UserDomainService.CreateAsync(userName, email)
```

Although the method does not take:

```csharp
CreateAsync(User user1, User user2)
```

the uniqueness rule actually concerns:

```text
New User
   +
Existing Users
```

so the rule extends beyond the boundary of a single User Aggregate.

## ApplicationService

`ApplicationService` is responsible for **Use Case Orchestration**.

For example, registering a user:

```csharp
public sealed class RegisterUserHandler
{
    private readonly UserDomainService _userDomainService;
    private readonly IUserRepository _users;
    private readonly IUnitOfWork _unitOfWork;

    public async Task<UserId> Handle(
        RegisterUserCommand command,
        CancellationToken cancellationToken)
    {
        var user = await _userDomainService.CreateAsync(
            command.UserName,
            new Email(command.Email),
            cancellationToken);

        await _users.AddAsync(
            user,
            cancellationToken);

        await _unitOfWork.SaveChangesAsync(
            cancellationToken);

        return user.Id;
    }
}
```

The Application layer is responsible for:

```text
RegisterUserHandler
        │
        ├── Call UserDomainService
        │          │
        │          ├── Check email uniqueness
        │          ├── Check user name uniqueness
        │          └── Create User
        │
        ├── Repository.Add(User)
        │
        └── SaveChanges
```

It is important to distinguish:

```text
UserDomainService
    “What business rules must be satisfied to create a User?”

RegisterUserHandler
    “What steps are needed to complete the Register User use case?”
```

The former is a **Domain Rule**; the latter is **Orchestration**.

## Decision Guide

Use the following guide when deciding where business logic belongs:

```text
                      Logic
                        │
                        ▼
                 Is it a business rule?
                   /        \
                 No          Yes
                 │            │
                 ▼            ▼
          Application /   Can a single Aggregate
          Infrastructure   handle it?
                          /         \
                        Yes          No
                         │            │
                         ▼            ▼
                     Behavior    DomainService
```

Typical call flow:

```text
                    ApplicationService
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
          Behavior                DomainService
              │                         │
              ▼                         ▼
       Single Aggregate       Multiple Aggregates /
                              Aggregate-wide Facts
```

## Architecture Rules

### Rule 1 — Entity owns State

Aggregate Roots, Entities, and Value Objects primarily express domain state.

```text
Entity = State
```

### Rule 2 — Behavior owns Aggregate Behavior

`Behavior` is responsible for business behavior and state transitions within a single Aggregate Boundary.

```text
Order → OrderBehavior
User → UserBehavior
```

### Rule 3 — DomainService owns Rules Beyond an Aggregate

`DomainService` is responsible for domain rules that cannot be completed using only the state of one Aggregate.

These include:

```text
Cross-Aggregate Rule
Aggregate-wide Rule
Uniqueness Rule
Rule requiring a query of another Aggregate
```

`DomainService` can depend on a Repository abstraction to obtain the necessary domain facts.

### Rule 4 — Application owns Orchestration

`ApplicationService` is responsible for:

```text
Load
Coordinate
Call Domain
Persist
Publish
```

but should not implement Domain Rules.

### Rule 5 — Infrastructure owns Technical IO

Concrete technical implementations such as database, HTTP, message queues, and Redis belong in Infrastructure.

The Domain layer can depend on a Repository abstraction, but must not depend on concrete:

```text
DbContext
SQL
HttpClient
Redis Client
MQ Client
```

### Rule 6 — Do Not Force Domain Logic

For simple CRUD operations with no Domain Rules, the flow can be:

```text
API
 ↓
Application
 ↓
Repository
```

There is no need to introduce a `Behavior` or `DomainService` artificially.

## Summary

The architecture can be summarized in four statements:

> **Entity stores state.**

> **Behavior implements business behavior within a single Aggregate boundary.**

> **DomainService implements business rules that go beyond a single Aggregate boundary.**

> **ApplicationService orchestrates the use case.**

In other words:

```text
Entity             = State
Behavior           = Single-Aggregate Behavior
DomainService      = Beyond-Aggregate Domain Rules
ApplicationService = Orchestration
```

Typical call flow:

```text
                    API
                     │
                     ▼
              ApplicationService
                     │
          ┌──────────┴──────────┐
          │                     │
          ▼                     ▼
      Behavior             DomainService
          │                     │
          ▼                     ▼
   One Aggregate       Cross-Aggregate Facts
          │                     │
          └──────────┬──────────┘
                     ▼
                  Entity
                     │
                     ▼
                Persistence
```

The goal of this architecture is not to implement a traditional Rich Domain Model. It keeps anemic Entities simple, easy to persist, and easy to understand, while preventing business rules from leaking into `ApplicationService`:

```text
State         → Entity
Local Rule    → Behavior
Global Rule   → DomainService
Workflow      → ApplicationService
Technical IO  → Infrastructure
```
