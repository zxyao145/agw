  - `Api`: Controllers, Consumers, DTOs
  - `Application`: Use cases, workflows
  - `Domain`: Business rules
  - `Infrastructure`: DB, Frameworks, APIs
- Anemic Domain Model
  - Domain objects contain only data — no business behavior.
  - all business behavior or method move into action

# Clean Architecture

## Layer Overview

- `Api`: Controllers, Consumers, DTOs
- `Application`: Use cases, workflows
- `Domain`: Business rules
- `Infrastructure`: DB, Frameworks, APIs

## Dependency Rule:

Dependencies must always point **inward**

`API → Application → Domain ← Infrastructure`

The Domain never depends on anything else.

## API Layer (Delivery Mechanism)

**Purpose:**

Converts **external input** into **application calls**.

It knows *how* users talk to the system.

### What belongs here

- Controllers
- EndpointRouteBuilder
- REST / GraphQL / gRPC Protocol conversion
- Request & Response DTOs
- Authentication
- Routing
- Validation

### Must NOT contain

- Business rules
- Domain logic
- Database logic

## Application Layer (Use Cases)

**Purpose:**

Defines **what the system can do**.

It coordinates domain objects to perform business actions.

> If Domain is what is allowed, Application is what happens when the user does X.

### What belongs here

- Use cases (services)
- Command & Query handlers
- DTOs
- Interfaces for repositories
- Transaction management
- Business workflows

### Must NOT contain

- SQL
- HTTP
- Controllers
- UI logic
- Framework code

## Domain Layer (The Core)

**Purpose:**

Contains the **business rules and logic** that define what your system *is*.

This layer must be **pure and framework-free**.

### What belongs here

- Entities
- Value Objects
- Domain Services / Actor
- Business rules
- Domain Events
- Interfaces （<Domain>Repository, etc.)

### Must NOT contain

- Database code
- HTTP
- JSON
- Controllers
- UI
- Frameworks (Spring, [ASP.NET](http://ASP.NET), etc.)
