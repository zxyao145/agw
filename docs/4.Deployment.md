# Agw Server Deployment

Agw publishes three ASP.NET Core images. `agw` is the combined Standalone Host, `agw-control-plane` owns setup/Web/management/Job scheduling, and `agw-data-plane` owns SignalR Execution, A2A, and distributed workers. Node.js is required only while building the Control Plane and Standalone Web assets.

## Data directory

Portable releases store mutable data in the current user's `agw` directory:

- Windows: `%USERPROFILE%\agw`
- macOS and Linux: `~/agw`
- Container: `/data`

Set `AgwDataDir` in the Host's `appsettings.json` to override the default:

```json
{
  "AgwDataDir": "/srv/agw",
  "AgwLogDir": "./logs"
}
```

The same key follows the standard configuration chain: base JSON, environment-specific JSON, development Secrets, environment variables, then command-line arguments (for example `--AgwDataDir=/srv/agw`). Missing or blank values use the user-home default; `~`, `~/...`, and `~\...` expand to the current user home on all platforms; other relative paths resolve against the process working directory. Host startup and password reset use this configuration; EF tooling reads its host JSON and environment variables for data paths as well. Data paths are fixed at startup: restart after changing the root, and move existing state and keys yourself when relocating an installation.

Logs use the independent `AgwLogDir` setting, defaulting to `./logs` relative to the process working directory, even when `AgwDataDir` is changed. Missing or blank values use that default. It supports `~` expansion and standard JSON/environment/command-line precedence (for example `--AgwLogDir=/var/log/agw`). Restart after changing it; existing logs are not moved automatically. Container deployments that persist file logs must mount this directory separately.

Back up the database (including `setting` and `api_token`), `skills/`, and `keys/` together, and retain the deployment configuration and its secret references separately. Logs and temporary files do not need to be restored.

## Project workspaces

`Project.Workspace` is not copied into the Agw data directory. It must name a directory visible to the Server process; the file API, Git commands, Claude Code, and Codex all use that same working tree.

For network storage, mount it through the operating system or container platform before starting Agw, then configure the mount path as the Workspace. The mount must provide the locking, rename, and consistency semantics required by Git. Containers need an explicit bind mount, and every execution replica must see the same path. Agw does not provide an application-level SFTP backend.

The file-system resolver caches a Project after its first use. Restart the Server after changing an already-resolved Workspace.

## Portable Server

Portable releases contain the Standalone Host. Start them with `agw-server serve` (`agw-server.exe serve` on Windows). Running without the `serve` argument remains supported. It listens on `http://127.0.0.1:30816` unless `ASPNETCORE_URLS` is set.

Reset a forgotten administrator password while the Server is stopped:

```bash
agw-server auth reset-password
```

## Standalone container

Build and run the combined Standalone image:

```bash
PUBLISH_MODE=docker APP_VERSION=0.1.0 IMAGE_NAME=agw:0.1.0 ./publish.sh
docker load -i artifacts/publish/docker/agw-server-0.1.0-linux-arm64.tar
docker run --rm -p 127.0.0.1:30816:8080 -v agw-data:/data agw:0.1.0-arm64
```

The default build writes Standalone, Control Plane, and Data Plane archives for Linux amd64 and arm64. Standalone and Control Plane contain the statically exported `@agw/web` application; Data Plane does not. Set `DOCKER_PLATFORMS` to restrict the local build to one platform.

## Split Control/Data deployment

Use `ghcr.io/zxyao145/agw-control-plane:<version>` and `ghcr.io/zxyao145/agw-data-plane:<version>` with PostgreSQL. Provide both roles with the same standard deployment configuration. Start one Control Plane for initial Setup, wait for readiness, then scale Control Plane replicas and start Data Plane replicas. All roles read initialization and authentication state from the shared database; browser Setup requires no extra restart.

Both roles must share Data Protection keys and runtime credentials, and they must see the same `Project.Workspace` paths. All roles use the global `auth` group of `setting` in the shared database. Deployment settings come from the standard appsettings configuration chain; no Host uses an authentication state file.

The shared `Agw.Host` owns runtime Data Protection registration, sets the application name to `Agw`, and persists keys under `<AgwDataDir>/keys`. Infrastructure and Integrations consume the Host-provided `IDataProtectionProvider`; they do not register a default provider. Tests that assemble these modules independently must provide Data Protection explicitly. The EF design-time factory creates its own provider with the same application name and resolved key directory.

External Nginx or another ingress owns routing. Route `/api/hubs/exec`, `/a2a/*`, and `/.well-known/agents.json` to Data Plane; route all remaining paths to Control Plane. Preserve the original Host, authentication headers/cookies, WebSocket upgrade headers, and omit the SignalR query string from access logs. See `deploy/compose.cluster.yaml` and `deploy/nginx.split.conf.example`.

Control Plane schedules Jobs and registers them as durable executions. Data Plane workers claim and run them. A2A uses the same durable execution state and event stream in split deployments; A2A human interaction is rejected explicitly rather than left waiting.

To publish a multi-platform manifest, log in to the registry and provide every desired tag through `IMAGE_TAGS`:

```bash
PUBLISH_MODE=docker \
APP_VERSION=0.1.0 \
IMAGE_NAME=ghcr.io/zxyao145/agw:0.1.0 \
IMAGE_TAGS="ghcr.io/zxyao145/agw:0.1.0 ghcr.io/zxyao145/agw:latest" \
DOCKER_PUSH=true \
./publish.sh
```

`IMAGE_TAGS` accepts spaces, commas, or newlines. `APP_VERSION` is also written into the Server assembly and OCI image metadata.

`IMAGE_NAME`/`IMAGE_TAGS` configure Standalone. Control Plane and Data Plane repository names default to the Standalone repository with `-control-plane` and `-data-plane` suffixes; override their complete tag sets with `CONTROL_PLANE_IMAGE_TAGS` and `DATA_PLANE_IMAGE_TAGS` when publishing aliases.

## Deployment configuration and first run

Database, execution mode, and locks are standard configuration. For a Standalone SQLite installation, these complete settings can be written directly in `appsettings.json`:

```json
{
  "Database": {
    "Provider": "sqlite",
    "ConnectionString": "Data Source=agw.db"
  },
  "Execution": { "Provider": "InProcess" },
  "DistributedLock": { "Provider": null, "ConnectionString": "" }
}
```

These are also the built-in defaults; the SQLite file resolves to `/data/database/agw.db` in containers. Relative SQLite paths resolve under the data directory's `database/` folder. The base JSON template omits these five keys and standard configuration overrides the built-in defaults.

Configuration priority, lowest first: built-in defaults → `appsettings.json` → environment JSON → configured Development User Secrets → environment variables → command line. Overrides are per key, so a database change needs both `Database:Provider` and `Database:ConnectionString`; review execution and locks at the same time. Apply coordinated deployment changes by restarting all affected roles.

Standalone, Control Plane, and Data Plane can start without `server-state.json`. The `/setup` page on Standalone and Control Plane asks only for an administrator password. Remote or forwarded access also requires the one-time Setup Code printed in the startup log; direct localhost setup does not. Database initialization uses the effective standard configuration, and successful setup enters the application immediately. Data Plane reads deployment settings from appsettings and does not host Setup.

For unattended Standalone initialization, inject the administrator password:

```yaml
services:
  agw:
    environment:
      Setup__AdminPassword: "${AGW_ADMIN_PASSWORD}"
```

For a PostgreSQL Cluster, configure both roles with the same runtime settings, and supply the initial administrator password only to Control Plane:

```yaml
x-deployment-environment: &deployment-environment
  Database__Provider: postgres
  Database__ConnectionString: "${AGW_DATABASE_CONNECTION_STRING}"
  Execution__Provider: Distributed
  DistributedLock__Provider: postgres
  DistributedLock__ConnectionString: ""
services:
  control-plane:
    environment:
      <<: *deployment-environment
      Setup__AdminPassword: "${AGW_ADMIN_PASSWORD}"
  data-plane:
    environment:
      <<: *deployment-environment
```

`AGW_DATABASE_CONNECTION_STRING` is a complete Npgsql connection string, for example `Host=postgres;Port=5432;Database=agw;Username=agw;Password=<secret>;Application Name=agw-server`. Use Npgsql quoting for passwords containing connection-string delimiters. In `deploy/compose.cluster.yaml`, its credentials must match the PostgreSQL service's `AGW_POSTGRES_PASSWORD`. Inject the complete connection string and administrator password through Secrets rather than committing real credentials. Start the Compose Control Plane first, wait for readiness, then start Data Plane; dependency ordering alone does not wait for setup completion.

Database connection strings are parsed at Host startup for the selected provider. PostgreSQL requires a nonempty `Host`; overriding only the provider while inheriting the SQLite connection string is rejected. SQLite allows an empty connection string to use its default data path. Validation does not open a database connection or require password authentication. PostgreSQL examples explicitly set `Application Name=agw-server` for identification in `pg_stat_activity`; user-provided connection strings are preserved, and Npgsql can also use `PGAPPNAME` when no application name is specified.

Unattended startup validates configuration and runs database migration, seeding, password hashing, and insertion of the administrator record before accepting traffic. Failure exits the container without completed state. Once initialized, Setup configuration is ignored and cannot overwrite a changed administrator password. Only `Setup:AdminPassword` is supported; old deployment fields under Setup are rejected on an uninitialized Server and must be replaced by standard Database/Execution/DistributedLock settings.

Initialization and administrator password/session state live in the global `auth` group of `setting`. The row is created only after successful database migration and seeding. Password changes increment its session version; all replicas refresh from the database once per second and discard cached credentials on read failure. No Host reads or writes `server-state.json`, imports its Tokens, or uses its deployment settings.

## Desktop development CORS

The packaged Desktop renderer is served from the `agw://app` origin, which the Server allows by default. The Desktop development renderer uses `http://localhost:3000` (or `http://127.0.0.1:3000`); these origins are allowed automatically when the Server runs in the `Development` environment.

The allowlist is configured as `Auth:AllowedOrigins` in the Host appsettings. The base configuration contains only the packaged Desktop origin:

```json
{
  "Auth": {
    "AllowedOrigins": [
      "agw://app"
    ]
  }
}
```

The Development appsettings adds the local Renderer origins. If a development Desktop connects to a Server running in another environment, add the required origins to that environment's appsettings and restart the Server. The CORS policy and SignalR WebSocket Origin validation use the same allowlist.

## History and telemetry

The Host template uses `ConversationHistory:Mode=Interval` and `FlushIntervalSeconds=10`; omitting the interval key uses the code fallback of 5 seconds. Buffer and event-write settings are described in [conversation persistence](operations/conversation-persistence.md).

The template leaves `OpenTelemetry:OtlpEndpoint` blank. Host startup treats blank or missing as `http://localhost:4317`, so an empty value does not disable OTLP export. Set `OpenTelemetry__OtlpEndpoint` to the collector address for that deployment.

## Distributed execution

Distributed deployments, including both split Host roles, must provide these settings:

```bash
Execution__Provider=Distributed
Database__Provider=postgres
DistributedLock__Provider=postgres
Execution__Distributed__EventStream__Provider=Postgres
```

An empty `DistributedLock__ConnectionString` reuses the application PostgreSQL connection. PostgreSQL is also the default execution event stream, so Redis is optional. To use Redis replay, set `Execution__Distributed__EventStream__Provider=Redis` and provide `Execution__Distributed__EventStream__Redis__ConnectionString`.

All replicas must share the database, Data Protection key ring, and host-visible Project Workspace paths. Distributed execution resumes work with at-least-once semantics; Tools with external side effects must be idempotent. Plan retention for `durable_execution` and PostgreSQL `execution_stream_entry` records, or configure the Redis stream TTL. See the [Execution subsystem README](../src/server/Agw.Agents.Execution/README.md) for worker, recovery, replay, and Human-in-the-loop details.

## Automated releases

`.github/workflows/build-desktop.yml` builds and tests the Desktop matrix for relevant pull requests, every push to `main`, manual runs, and calls from the release workflow. These builds upload temporary Actions artifacts only.

`.github/workflows/release.yml` runs for supported version tags or a manual `release_tag`. Accepted forms are `vX.Y.Z` and `vX.Y.Z-{preview|alpha|beta}.N`. It builds all Desktop installers, publishes `linux/amd64` and `linux/arm64` Server images, and creates or updates the matching GitHub Release. Stable releases receive exact, minor, major, `latest`, and commit-SHA image tags; prereleases receive only the exact version and commit-SHA tags and are marked as GitHub prereleases. A manual tag that does not yet exist is created at the selected workflow revision.

## Domain access

Terminate TLS with Caddy or Nginx on the host and proxy to `127.0.0.1:30816`. Keep the Agw HTTP port bound to loopback, preserve the original Host, and forward scheme/client headers. Set `AllowedHosts` to the public hostname. Loopback proxies are trusted by default; add any other proxy IP through `ReverseProxy__TrustedProxies`. The Compose example uses a fixed Docker gateway and trusts only that gateway. See `deploy/Caddyfile.example`, `deploy/nginx.conf.example`, and `deploy/compose.yaml`.

SignalR uses the `access_token` query parameter for authenticated browser WebSocket handshakes. Configure reverse-proxy access logs to record the path without its query string; the Nginx example uses `$uri` instead of `$request_uri` or `$request` for this reason.

Agw v1 supports a dedicated domain root such as `https://agw.example.com/`. Deploying below a path such as `/agw` and direct certificate management by Agw are not supported. SQLite is limited to Standalone mode. Cluster mode requires all replicas to use the same PostgreSQL database and PostgreSQL advisory locks; an omitted lock provider follows the database, and an empty lock connection string reuses the application database connection.

## Upgrading existing installations

Server, Web, Desktop, and Mobile must be upgraded together. Runtime compatibility with historical formats has been removed:

- Replace the old `AGW_DATA_DIR` environment variable with `AgwDataDir`, retaining the same mounted directory and Data Protection keys. The old name is ignored.
- Agent/Project Tools must already use the current typed object format. String arrays and the removed `bash`, `powershell`, and `generate_guid` definitions are rejected; the current shell Tool is `run_shell`. Startup no longer rewrites old default Agent Tool selections.
- Complete or interrupt old in-flight executions before upgrading. Durable recovery requires explicit owner, workspace snapshot, and matching indexed Project/Conversation scope. Missing fields and unindexed rows are not backfilled or scheduled. This change does not delete historical records or provide a data conversion.
- Mobile reads current Server Profiles only. Re-add a server or use manual configuration import when only the old local configuration exists; its original stored value is left untouched.
- Desktop uses `/desktop/chat`; its old `/chat` entry is removed. Existing Agentflows without an Input node fail validation rather than acquiring generated nodes and edges.

This cleanup changes no EF model, database columns, indexes, or existing migrations. Back up data before any separately managed conversion; do not manually stamp ownership flags to bypass runtime validation.

The `AddSettings` migration directly creates the audited `setting` table and its global/user unique indexes. For installations using the removed JSON state store, explicitly configure Database/Execution/DistributedLock, apply the provider-specific migration, and initialize the administrator once through Control Plane `/setup` or a securely injected `Setup__AdminPassword`. Existing database API Tokens remain intact; JSON-only Tokens and the old administrator password/session state are not imported. Keep the old file in a backup for rollback, but it is no longer a runtime dependency. Coordinate the upgrade across all replicas before exposing the new setup endpoint. Back up settings before rolling back `AddSettings`, which drops the table.

Stop the old Server and back up the complete Agw data directory before upgrading. First-run setup applies the selected database provider's pending migrations, but an already initialized installation does not rerun setup migrations during a normal startup. Apply the matching SQLite or PostgreSQL migrations through the deployment's database-change process before starting the new Server. Source deployments can use the commands in the [Development Guide](1.Development.md); do not apply both provider migration sets or edit EF migration history manually. Scope indexes, conversation Generation, session bindings, and recovery verification are covered in [runtime consistency maintenance](operations/backend-runtime-consistency.md).

升级到统一 Turn 执行机制时，需要停止全部旧版 Control Plane、Data Plane 和 Standalone 进程，再执行对应 Provider 的 migrations，并启动新版 Host。保留现有 Data Protection key ring。已初始化的 Host 在监听请求和启动 Worker 前，通过共享应用锁执行可重复运行的数据升级：验证活动执行的所属用户、工作目录清单和对话 Generation；将输入及历史关联到 `TurnId = executionId`；保留 checkpoint 和已提交的人工回答；将没有租约的旧 `Running` 执行调整为可恢复状态。等待人工回答的执行会在持久化事件中保留尚未回答的请求。每条执行记录通过独立事务完成转换。记录无法解密或验证失败时，Host 启动报错；按照部署环境的数据维护流程修正记录后重新启动。新执行以 `Queued` 状态登记，取得本地并发名额后领取租约，本地请求与 Worker 共用 `MaxConcurrentExecutions`。

The `AddModelCompactionLimits` migration makes these model-schema changes:

- renames `model.max_tokens` to `model.max_context_window_tokens` while preserving every existing value;
- adds `model.max_output_tokens` with a default of `64,000`;
- requires both limits to be positive and `max_output_tokens < max_context_window_tokens`.

The migration contains no custom data rewrite. Before applying it, verify that every existing `max_tokens` value is greater than `64,000`; if an installation contains an incompatible value, correct it manually before migration. After upgrading, review both limits on the Models page and set them to each provider's actual specifications. The `256,000 / 64,000` defaults used for new or automatically discovered models are only fallbacks for automatic Definition Agent compaction.

The model-management JSON contract changes at the same boundary: clients must send `maxContextWindowTokens` and `maxOutputTokens`. The former `maxTokens` field has no compatibility alias.

For installations that predate the current data-directory and setup layout:

- SQLite: copy the old database to `agw/database/agw.db`, or specify its absolute Server path in `Database:ConnectionString`.
- PostgreSQL: supply the existing database connection string through `Database:ConnectionString` and set `Database:Provider=postgres`.
- Skills: copy the old `wwwroot/skills` contents to `agw/skills`.
- Authentication: the old `X-API-Key` is not migrated. Create a new administrator password and named API Tokens.


## OIDC login

OIDC login is optional. Existing administrator password and named Token access remain available when no providers are configured. New OIDC accounts automatically become ordinary, isolated local users, starting at ID `10000`. The administrator remains `1001`; there is no email-based account linking or IdP-role-to-administrator mapping.

Register Agw as a **Web/confidential client** at each IdP, including when the end user uses Desktop. The IdP redirects to Server, not directly to the Desktop protocol.

For a provider named `company`, register:

```text
https://agw.example.com/api/auth/oidc/callback/company
```

Set the public URL to the browser-visible Web/ingress origin. Preserve the original scheme and Host at the trusted reverse proxy. In a split deployment, route all OIDC and Desktop login endpoints to Control Plane; Data Plane serves execution with the resulting local credentials.

Example non-secret OIDC configuration:

```json
{
  "Auth": {
    "Oidc": {
      "PublicBaseUrl": "https://agw.example.com",
      "Providers": {
        "company": {
          "Enabled": true,
          "Type": "Oidc",
          "DisplayName": "Company account",
          "Authority": "https://sso.example.com/realms/company",
          "ClientId": "agw"
        }
      }
    }
  }
}
```

Inject `Auth__Oidc__Providers__company__ClientSecret` through environment variables or your secret manager. Do not put real secrets in appsettings, frontend environment files, screenshots, or source control. Provider IDs use lowercase kebab-case and remain stable; each ID has its own callback path.

OAuth2 providers use `Type: "OAuth2"` and configure explicit endpoints. For GitHub:

```json
{
  "Auth": {
    "Oidc": {
      "PublicBaseUrl": "http://127.0.0.1:30816",
      "Providers": {
        "github": {
          "Enabled": true,
          "Type": "OAuth2",
          "DisplayName": "GitHub",
          "AuthorizationEndpoint": "https://github.com/login/oauth/authorize",
          "TokenEndpoint": "https://github.com/login/oauth/access_token",
          "UserInfoEndpoint": "https://api.github.com/user",
          "Issuer": "https://github.com/login/oauth",
          "IdentitySource": "UserInfo",
          "UsePkce": true,
          "ClientAuthMethod": "Post",
          "Scopes": ["read:user"],
          "SubjectClaim": "id",
          "DisplayNameClaim": "login",
          "EmailClaim": "email",
          "ClientId": "github-client-id"
        }
      }
    }
  }
}
```

For OAuth2, `ClientAuthMethod` is `Post` or `Basic`; `IdentitySource` is `UserInfo` or `AccessToken`. `AccessToken` requires a signed JWT access token plus `AccessTokenIssuer`, `AccessTokenAudience` and `AccessTokenJwksUri`. `UsePkce` defaults to false and only enables S256 when true. The C# implementation uses enums; configuration uses these string values. See [OAuth2 design](approachs/2026-09-18-oauth2.md) for all combinations.

Typical Authority values:

| Platform | Authority |
| --- | --- |
| Google | `https://accounts.google.com` |
| Microsoft Entra ID | `https://login.microsoftonline.com/<tenant-id>/v2.0` |
| Keycloak | `https://sso.example.com/realms/<realm>` |
| Authentik | `https://sso.example.com/application/o/<application-slug>/` |

Use a tenant-specific Entra Authority. OIDC providers use Authority and request `openid profile email`; OAuth2 providers use their explicit endpoints and configured scopes. Missing display name/email does not prevent authentication. Test the provider registration before enabling access.

Production URLs require HTTPS. Development can use HTTP loopback for both the public origin and a local test IdP. Changing configuration requires restarting the relevant Hosts. Disabling a provider blocks new login and pending Desktop exchange; it does not revoke already-issued local credentials.

Web uses the Agw session Cookie. Desktop opens the system browser, receives a two-minute one-time code, and submits its own verifier to Server for an Agw Token. `agw-desktop://auth/complete` is the Server-to-Desktop handoff address; it is not the IdP callback. The existing `agw-desktop://oauth/complete` integration callback remains separate.

All replicas share the SQL database and Data Protection keys. The handoff table permits callback and exchange on different replicas without sticky sessions or Redis. Exchange consumption and Token creation are transactional. Expired grants are cleaned once per minute in batches of up to 1000.

Before rollout, back up the database and validate the matching SQLite/PostgreSQL migrations using the provider-specific commands in [Development](1.Development.md). The OIDC migration adds four Auth-owned tables and preserves existing business ownership and Tokens; it adds no foreign keys. Coordinate all Host versions before enabling providers. Rolling back an application should leave the additive tables in place; dropping them after real users register would lose identity mappings.

Do not include authentication query strings in ingress access logs. Framework OIDC/OAuth2 protocol errors remain at `Error` for configuration and callback diagnostics; do not enable verbose protocol logging in production. Inspect login result, callback duration, Token exchange, UserInfo/JWT validation, Desktop exchange and cleanup metrics. A failed login must never be worked around by disabling issuer, audience, signature, state, nonce or PKCE checks.


### OIDC security and upgrade notes

The Agw session Cookie changes from SameSite=Strict to Lax for both administrator and OIDC sessions, allowing an existing session on cross-site top-level navigation. This is separate from the OIDC correlation/nonce Cookies used to validate the callback. Cookie-authenticated POST/PUT/PATCH/DELETE requests still require antiforgery validation, except documented endpoints using their own proof; GET endpoints must not mutate business data. Lax is an intentional navigation tradeoff, not a requirement to relax every Cookie merely because OIDC is enabled.

Before upgrading a customized deployment, inventory Token owners without reading Token hashes:

```sql
SELECT DISTINCT create_by FROM api_token ORDER BY create_by;
```

The standard previous login flow uses administrator ID 1001. Do not assume imported or customized deployments contain only that ID. Numeric owners >=10000 must have a valid corresponding auth_user row after migration; otherwise their Tokens are rejected. If such owners already exist, resolve their identity mappings and reserve the existing numeric range before opening registration (the allocator must be greater than existing IDs and at least 10000). Do not automatically provision users from Token owners or disable this fail-closed check. Back up and explicitly migrate custom ownership mappings; the standard OIDC migration does not infer them.

OIDC failure logs under Agw.Auth.Oidc now contain ProviderId, Client, Stage, FailureCategory, ExceptionType and TraceId. The agw.auth.oidc.failure counter adds bounded stage/category labels. Stages distinguish challenge, protocol-validation, token-exchange, token-validation, provisioning, desktop-grant and session. Categories distinguish provider-unavailable/provider-timeout, invalid-nonce/invalid-state/invalid-token/protocol-rejected, generic protocol-validation-failed and local completion failures. A generic protocol failure is not evidence that state alone failed. Search by TraceId and stage before checking provider configuration or database health. Exception messages, raw upstream responses and credentials remain excluded; do not enable raw framework logs as a routine diagnostic shortcut.
