# Agw 事件中心与 TaskPilot extension 需求文档

## 1. 目标与设计约定

建设通用事件中心，为 Agent、Agentflow 和 Server extension 提供事件接入、持久保存、订阅、可靠投递和定时唤醒能力。

通过原生 TaskPilot（任务领航）extension 提供持续跟进事项、多轮执行、人工决策、定时复查和 GitHub PR 自动交付。通过独立的飞书 extension 提供通知和卡片交互。

本次完全采用新的领域模型、API、数据库结构和管理界面，兼容性要求为零。

已经确定的产品行为：

- MQ 提供 InProcess 和 Redis Streams 两种实现。
- 提供通用 HTTP JSON 轮询，首次扫描建立基线。
- 飞书支持群机器人 Webhook 和企业自建应用。
- Desktop 离线期间保留通知记录，重新连接后通过界面查看。
- TaskPilot 提问时结束当前轮次，回答后创建后续轮次。
- TaskPilot 包含自主跟进和 PR 自动交付，提供 Desktop extension 管理界面。

## 2. 仓库分析与领域职责

`agent-autoloop` 已经实现了三个需要保留的业务机制：

- **持续事项与事件合并。** 当前通过 `rule + lane` 关联同一事项，排队期间收到的事件合并进入一轮；执行期间收到的事件等待后续轮次。参见[事件排队与合并](/Users/ben/source/repos/agent-autoloop/kernel/decide.ts:183)。
- **结构化回执驱动后续工作。** 回执可以提出问题、发送通知、结束卡片、预约复查和发布事件；人工回答和复查到期会触发后续轮次。执行输入还区分了可信规则和外部资料。参见[执行输入与回执](/Users/ben/source/repos/agent-autoloop/worker/contract.ts:28)。
- **完整的 PR 交付过程。** 包括读取目标分支配置、审查指定提交、等待检查、核对提交变化、合并、跟踪 Ship、核实健康版本和清理交付标签。参见[PR 交付实现](/Users/ben/source/repos/agent-autoloop/plugins/delivery/delivery.ts:115)。

集成后的职责归属：

- **事件中心**拥有 `EventSource`、`Event`、`Subscription`、`EventDelivery` 和定时事件，负责通用事件处理。
- **Agw 执行系统**负责 Agent、Agentflow、执行权限、会话、取消和执行结果。
- **TaskPilot extension**拥有 `Rule`、`Matter`、`Round`、`Receipt`、`Card` 和复查业务，负责持续跟进。
- **通知平台**负责通知记录、渠道选择、发送进度和交互动作传递；**飞书 extension**负责飞书接入。

`EventDelivery` 表示某个订阅处理事件的进度；`Round` 表示一次业务执行；`Matter` 可以跨多个轮次持续存在。各自独立记录状态。

## 3. 事件中心及平台支撑能力

### 3.1 事件来源

提供三种内置来源：

- **定时来源**：支持一次性时间、固定间隔和 Cron，明确使用的时区。
- **Webhook 来源**：支持来源认证、请求校验、数据映射和稳定事件标识。
- **HTTP 轮询来源**：支持请求方法、地址、请求头、请求体、认证、分页、结果集合提取、业务主键和变化识别。

轮询首次成功完成后保存基线，随后根据配置识别新增或变化。扫描进度必须在对应事件被可靠接收后推进。提供 GitHub issue 配置示例。

来源提供器可以通过 extension 扩展，新增来源使用统一的事件发布接口。

### 3.2 事件保存与订阅

每个事件记录来源、业务标识、类型、对象标识、发生时间、接收时间、payload、所属用户及处理链关联信息。

- 同一来源的相同业务标识重复提交，只接受一次。
- 没有订阅匹配的事件仍然保存。
- 一个事件可以匹配多个独立订阅。
- 订阅支持来源、事件类型和声明式字段条件。
- 订阅目标支持 Agent、Agentflow 和 extension 事件处理器。

事件中心提供来源配置、订阅配置、事件查询和投递进度管理界面，供 Web 与 Desktop 使用。

### 3.3 Transport 与可靠投递

定义统一的 `IEventTransport`，覆盖发布、消费、确认和未完成消息恢复，交付 InProcess 与 Redis Streams 两种适配器。

事件接收成功意味着事件及其待发布记录已经保存。消费者完成持久处理后确认消息。Redis Streams 使用 consumer groups、确认和 pending 消息恢复能力。[Redis Streams 文档](https://redis.io/docs/latest/develop/data-types/streams/)

事件传递采用至少一次语义，分别处理：

- 事件接入去重。
- 每个订阅的重复投递。
- extension 业务处理去重。
- 后续事件和通知发送去重。

extension 在自己的事务中保存业务状态、处理记录和待发送意图，再通过幂等接口发布后续事件。Server 重启后继续处理未完成记录。

### 3.4 定时事件

提供 `IEventScheduler`，支持创建、修改和取消持久定时事件。

定时记录具有所属用户、调用方、业务键、触发时间和关联信息。同一业务键重复提交具有幂等性，修改与取消可以查询结果。

TaskPilot 使用这项能力实现 `later`，保存事项、轮次和会话关联。定时事件到期后通过正常订阅投递。

### 3.5 Extension SDK 与执行入口

SDK 增加事件来源提供器、事件处理器和通知渠道提供器的注册能力。

处理器通过稳定的 `ExtensionId + HandlerId` 标识。每次调用由 Host 建立用户上下文并获取当前 generation lease。停用期间保留未完成投递，重新启用后继续处理。

平台向 extension 提供受身份约束的执行接口，覆盖：

- 幂等提交 Agent 或 Agentflow 执行。
- 查询状态和订阅结果。
- 取消执行。
- 关联 Project、Conversation 和会话续接信息。
- 获取当前执行身份，校验回执所属轮次。

来源采集、事件派发、TaskPilot 编排和通知发送运行在 ControlPlane；Agent、Agentflow 按 Agw 执行拓扑运行。Standalone 包含全部角色。多实例通过共享租约协调后台工作。

### 3.6 通知与交互

通知支持同时选择多个渠道，每个渠道独立保存发送状态、消息标识、版本、错误和重试记录。

- Desktop 展示在线期间产生的新通知，点击后进入对应 Server、事项或会话。
- Server 保存离线期间的记录，Desktop 重新连接后可以查看。
- 通知发送失败具有独立重试流程。
- 问题回答需要校验所属用户、回答者身份、原消息及问题状态。
- 同一个问题的首次有效回答生效，各渠道随后更新对应状态。

## 4. TaskPilot 与飞书 extension

### 4.1 TaskPilot 规则与事项

`Rule` 配置事件条件、执行目标、Project、可信指令、资料读取范围、权限、分组、并发数、会话策略和通知渠道。

同一规则根据业务对象关联 `Matter`：

- 同一事项的轮次串行执行。
- 排队期间的新事件合并处理。
- 执行期间的新事件进入后续轮次。
- 不同事项按照规则的并发上限执行。
- 回答和定时复查始终关联原事项。
- 支持暂停、恢复、立即运行和取消执行。

外部事件中的文字作为资料提供。执行目标、目录、权限和允许发布的事件类型由可信规则决定。

### 4.2 轮次与回执

`Round` 保存输入事件、规则版本、执行标识、会话、结果、错误、尝试记录和用量。

`Receipt` 支持：

- `ask`：创建问题卡片。
- `notice`：创建通知。
- `resolve`：结束已核实解决的卡片。
- `later`：预约、修改或取消复查。
- `events`：发布规则允许的后续事件。

回执整体校验后，在事务中保存处理结果和后续操作意图。同一回执重复提交只生效一次。

回执修正与业务执行分别处理；回执错误保留已经完成的业务结果，进入回执修正流程。

需要人工处理时，本轮结束并释放执行资源，事项保存等待状态。回答作为事件触发后续轮次，并携带原问题、回答、上下文和会话信息。

保留失败退避、连续失败通知、达到上限后停止及会话接续能力。完整记录每次尝试。

后续业务事件继承处理链；回执产生新事件时增加 `Hops`，回答和复查继承原深度。默认上限为 8，超出后保存事件并停止自动派发，同时通知用户。

### 4.3 PR 自动交付

支持 GitHub 交付规则，包含交付标签、仅审查模式、人工跟进通知策略及向用户提问。

交付过程需要：

- 从可信项目配置和目标分支读取交付规则。
- 生成指定提交的只读文本快照，交给配置的审查 Agent。
- 核对审查提交、目标分支和对应检查结果。
- 在合并前重新读取远端状态。
- 跟踪 Ship，并核实线上健康版本覆盖目标提交。
- 记录各阶段结果，支持失败后继续核实远端状态。
- 完成后更新交付状态和标签。

CI、发布和人工处理的等待过程通过持久状态及后续事件继续推进，期间释放 Agent 执行资源。

### 4.4 Desktop 管理界面

TaskPilot 以 Server/Desktop 组合 extension 提供：

- 规则配置和来源关联。
- 事项列表、当前状态与待执行动作。
- 轮次历史、输入事件、回执、错误和用量。
- 问题卡片回答及处理记录。
- 复查计划、暂停、恢复、立即运行和取消。
- PR 交付阶段与结果。

Server 在 Desktop 关闭后继续运行自主跟进。

### 4.5 飞书 extension

飞书作为独立 Server extension，注册通知渠道，封装 API 调用、凭证、签名、消息格式和交互接收。

提供两种接入：

- **群机器人 Webhook**：发送文本或卡片，提供进入 Agw 查看及处理问题的链接。
- **企业自建应用**：向用户或群聊发送消息，支持问题按钮、处理说明和卡片状态更新。

企业自建应用默认通过长连接接收 `card.action.trigger`；接收回调后及时确认，再通过持久事件推进业务处理。飞书要求回调在 3 秒内响应。[飞书回调文档](https://open.feishu.cn/document/event-subscription-guide/callback-subscription/receive-and-handle-callbacks)

同一应用的连接由多实例租约协调。飞书凭证保存在 Server，回答权限与 Agw 用户关联。

## 5. 验收场景

使用真实数据库、Redis 和实际组件验证以下场景：

1. 定时、Webhook、HTTP 轮询产生统一事件；首次轮询建立基线。
2. 重复接入、重复投递、重复回执和重复回答分别保持幂等。
3. InProcess 与 Redis Streams 通过相同的事件处理行为测试。
4. Server 在事件保存、派发和处理期间重启，已接受事件继续得到处理。
5. extension 停用、启用和 generation 更换后，投递记录与用户身份保持正确。
6. 同一事项正确合并排队事件，串行执行；不同事项遵守并发上限。
7. 提问后当前轮次结束；重启后回答问题能够触发正确的后续轮次。
8. 定时复查的创建、修改、取消及重启恢复保持正确。
9. 飞书与 Desktop 同时接收通知；首次有效回答生效，各渠道状态一致。
10. Desktop 离线通知可以查看，重新连接后按已确定的通知策略处理。
11. PR 审查、提交变化、检查、合并、Ship 和健康版本核实在专用测试仓库完成验收。
12. 用户隔离、事件发布权限、处理链深度及架构边界通过测试。

组件和集成检查通过后，再执行完整的“事件接入、事项处理、人工回答、后续执行、交付和通知”流程。
