# README

当前目录（approachs）下面存储的是历史技术方案，一旦已经进入到 git commit history，禁止修改。

- `1.Chat Suggestions.md` 和 `2.Agentflow.md` 是早期的技术方案，仅做留存。
- 文件命名格式为 `{yyyy-MM-dd}-{Technical Proposal name}.md`。
- 技术方案的内容格式，参考下面 `Technical Proposal Template` 章节。


## Technical Proposal Template

```markdown
# {技术方案}

## 名词解释

> 可选

## 背景

> 为什么需要这个设计？例如：
>
> - 产品需求
> - 用户反馈
> - 技术债（现在有什么问题）
> - 成本优化
> - 合规要求

## 设计目标

### 功能目标

> 列出所有功能。这里不做详细介绍，详细内容在 “详细设计” 章节体现。

### 技术目标

> 涵盖以下可能涉及的点：
> 
> - P99、SLA、CPU/内存使用率、延迟
> - 安全（认证、授权、校验、脱敏、审计日志等等）
> - 可观测（打点/指标、日志、告警）
> - 高可用（熔断、限流、降级、幂等、重试）

## 总体设计

> 一张整体交互的 **架构图**。大型方案设计需要，中小需求直接详细设计即可。  
> 如果有多种方案，需要放方案对比与技术选型

## 数据库设计

> - ER 图
> - 表结构
> - 索引
> - 字段说明
> - Migration SQL
>
> 如果大型方案，可以在详细设计中，为每个模块单独设计一章数据库设计。

## 详细设计

> 全文重点，按照`设计目标-功能目标`章节，对每个`功能目标`设计一个子章节写。

### {功能目标名称}

> 含有以下内容：
>
> - 方案对比与技术选型（如涉及）
> - 图片（如涉及），以解释数据如何流转。
>   * 时序图
>   * 流程图
>   * 状态图
> - 算法（如涉及）
>   * 原理
>   * 时间复杂度
>   * 为什么这样设计
> - 配置项（如涉及）。说明每个配置项
>   * key
>   * value
>   * 默认值
>   * 使用说明
> - 安全设计（如涉及）
> - 缓存（如涉及）
> - 可观测性（如涉及，也可以把监控、告警单独拎出来作为一章）
>   * 指标/打点
>   * 日志
>   * 链路追踪
>   * 监控看板
>   * 告警
> - 兼容设计（如涉及）

## 接口文档

> 如果比较多，可以单独放到一个文档中

### 基础信息

> - 域名
> - 环境信息
> - 认证与授权
> - 请求头、响应头
> - 协议规范
> - …

### 接口列表

> 接口信息：
>
> - method
> - path
> - 请求示例（json）
> - 响应示例（json）
> - 其他说明
>   * 新增接口还是修改接口
>   * 修改兼容性
>   * client 注意事项

## 测试计划

### 配置测试（可选）

> 如果涉及配置的增加、修改或删除，用来对系统的配置进行测试。

### 单元测试

> 描述对业务逻辑的测试用例，包含：  
> 测试用例名、用例描述或目的、前置条件、操作步骤等信息

### 集成测试（可选）

### 回归测试（可选）

```
