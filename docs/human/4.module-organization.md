# Module Organization

Agw is a modular monolith organized with Clean Architecture layers. Modules create only the layers they actually need; empty layers and a full reproduction of every Clean Architecture convention are not required.

## Backend Architecture and Module Layers

Backend modules are organized by business domain, with the following dependency direction within each module:

```text
Api → Application → Domain ← Infrastructure
```

Each module creates only the layers it needs.

- **Api layer:** Contains Controllers, Endpoints, DTOs, and Validators.
- **Application layer:** Contains use cases, workflows, service orchestration, and calls to Domain rules.
- **Domain layer:** Contains anemic entities, value objects, framework-free Behaviors, and DomainServices that span entity boundaries.

## Cross-Module Calls

The required path for cross-module calls is:

```plaintext
Calling module
→ Interface in Agw.<Module>.Contracts
→ Facade owned by that module (registered in its Add<Module>())
→ Internal AppService or I<Module>DbContext
```

Unless otherwise specified, cross-module calls may only go through an interface in the other module's `Agw.<Module>.Contracts` project. That module's Facade implements the interface.

- Contracts projects contain only interfaces and DTOs, and depend only on Agw.Shared or other Contracts projects.
- Do not reference the Application, Domain, or Infrastructure namespaces of another module.
- Do not reference another module's `*AppService`, `*RuntimeService`, or `I*DbContext`.

## Anemic Domain Model

Persisted entities, domain data objects, value objects, and similar types must remain anemic. Behavior required by the anemic model belongs in `Domain/Behaviors/<Entity>Behavior.cs` in the Module that owns the entity.

### Behavior Construction and Lifetime

Behavior gives an anemic model its behavior: `Behavior = the rich model of an aggregate root`.

```
public class Order
{
    public Guid Id { get; set; }

    public OrderStatus Status { get; set; }

    public List<OrderItem> Items { get; set; }

    public decimal TotalAmount { get; set; }
}

public class OrderBehavior
{
    private readonly Order _order;
    
    public OrderBehavior(Order order)
    {
        _order = order;
    }

    public void Submit()
    {
        if (_order.Status != OrderStatus.Pending)
            throw new DomainException("The order cannot be submitted in its current state.");

        if (_order.Items.Count == 0)
            throw new DomainException("An empty order cannot be submitted.");

        _order.Status = OrderStatus.Submitted;
    }

    public void Cancel()
    {
        if (_order.Status == OrderStatus.Completed)
            throw new DomainException("A completed order cannot be cancelled.");

        if (_order.Status == OrderStatus.Cancelled)
            return;

        _order.Status = OrderStatus.Cancelled;
    }
}
```

- An entity-bound Behavior **MUST** be a concrete `<Entity>Behavior` class and **MUST** be created manually with `new` by Application or DomainService code.
- A Behavior constructor binds exactly one aggregate root. Root-local preconditions MAY run before owned children are loaded; Application or DomainService code MUST load the complete consistency boundary before invoking any Behavior method that inspects or modifies those children.
- A Behavior may modify its bound aggregate root and its owned children. It MUST NOT modify external entities.
- Application or DomainService code MUST resolve external facts, time, and actor identity, then pass them to Behavior methods as values or read-only context.
- A Behavior **MUST NOT** be registered with IoC, cached, serialized, shared across threads, or reused across use cases.
- A Behavior **MUST NOT** define an `I<Entity>Behavior` Interface unless two real Adapters exist and the architecture decision has been explicitly approved.

### DomainService

A DomainService represents domain behavior that clearly belongs to a domain business rule but does not naturally belong to a particular aggregate root, Entity, or Value Object.

```
public sealed class UserDomainService
{
    private readonly IUserRepository _users;

    public UserDomainService(IUserRepository users)
    {
        _users = users;
    }

    public async Task<User> CreateAsync(
        string userName,
        Email email,
        CancellationToken cancellationToken = default)
    {
        if (await _users.ExistsByEmailAsync(
                email,
                cancellationToken))
        {
            throw new DomainException(
                $"Email '{email}' is already in use.");
        }

        if (await _users.ExistsByUserNameAsync(
                userName,
                cancellationToken))
        {
            throw new DomainException(
                $"UserName '{userName}' is already in use.");
        }

        return new User(
            UserId.New(),
            userName,
            email);
    }
}
```

## Persistence

Use modular DbContext interfaces. Each module declares its own `I<Module>DbContext` under that module's `Application/Persistence` directory. Each interface inherits `IModuleDbContext`, whose only member is `SaveChangesAsync`.

- An `I<Module>DbContext` interface contains only its inherited members and DbSet properties.
- Implementations of all `I<Module>DbContext` interfaces belong in the `Infrastructure` module (not in the current module's Infrastructure layer).
- Business modules access data only through their own `I<Module>DbContext`. For complex persistence logic that must be reused, or transactions spanning modules, declare an interface in `Application/Persistence` and implement it in `Agw.Infrastructure/<Module>/`.
- Persistence interceptors:
  - `EntityCreatorInterceptor`: sets `CreateBy` and `CreateTime`, and validates ownership.
  - `EntityModifierInterceptor`: prevents changes to `CreateBy`, validates ownership, and sets `UpdateBy` and `UpdateTime` while preserving values that were explicitly changed.
  - `EntitySoftDeleteInterceptor`: converts deletion of `ISoftDelete` entities into updates. No entities currently implement `ISoftDelete`, so all deletions are physical deletions.
- Database column names use `snake_case`.
- The database has no foreign keys. This is enforced through `NoForeignKeyModelDiffer`.
