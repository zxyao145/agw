# React Native Integration Design

Date: 2026-04-22
Project: Fe SwiftUI iOS app

## Goal

Integrate React Native into the existing SwiftUI iOS app as an embedded experience. The native SwiftUI app remains the primary shell, and multiple native buttons can open different React Native pages.

## Current Project Context

The app is a small SwiftUI project with:

- `Fe/FeApp.swift` as the app entry point.
- `Fe/ContentView.swift` as the only screen.
- `Fe.xcodeproj` generated by Xcode 26.4.1 using a file-system synchronized root group.
- No existing JavaScript, Node, CocoaPods, or React Native setup.

The project has Node, npm, and CocoaPods available locally. React Native 0.85 is the current stable release according to the React Native versions page on 2026-04-22.

## Selected Approach

Use one React Native runtime and one registered React Native module, then pass a route identifier from Swift to React Native through initial props.

SwiftUI presents a UIKit `ReactViewController` with a page configuration. The view controller creates a React Native view using `RCTReactNativeFactory` and passes the selected route and any page-specific props into JavaScript.

React Native registers one root module named `FeReactNative`. The root `App.tsx` reads `routeName` from initial props and dispatches to the matching RN screen component.

## Alternatives Considered

### Multiple AppRegistry modules

Each RN page could be registered as its own `AppRegistry.registerComponent` module. This is simple for the first few screens, but it spreads routing across Swift and JavaScript and makes page growth harder to maintain.

### Direct RCTRootView wrapping

SwiftUI could wrap a direct `RCTRootView` with `UIViewRepresentable`. This is less code, but React Native 0.85 documents `RCTReactNativeFactory` as the lifecycle entry point for existing iOS apps.

### React Native as the root app

The app could boot straight into React Native with Swift only acting as a native shell. This does not match the chosen scope because the existing SwiftUI app should remain the primary entry point.

## Native Architecture

Add a small native boundary for RN presentation:

- `ReactNativePage`: a Swift value describing a page, with `routeName`, `title`, and `initialProps`.
- `ReactNativeView`: a `UIViewControllerRepresentable` that presents `ReactViewController` from SwiftUI.
- `ReactViewController`: a UIKit controller that owns `RCTReactNativeFactory` and loads the `FeReactNative` module with page props.

`ContentView` will show several native buttons. Each button opens a different `ReactNativePage`, for example:

- `home`
- `settings`
- `details`

The page list should be plain Swift data so adding a new native entry point does not require duplicating presentation code.

## JavaScript Architecture

Add a minimal React Native project surface at the repository root:

- `package.json`
- `package-lock.json`
- `index.js`
- `App.tsx`
- `metro.config.js`
- `.watchmanconfig`

`index.js` registers the module:

```js
AppRegistry.registerComponent('FeReactNative', () => App);
```

`App.tsx` reads:

- `routeName`
- `title`
- any other page-specific props

It maps `routeName` to screen components. Unknown route names render a small fallback screen that shows the missing route, rather than crashing.

Initial screens can be simple but distinct, so the integration proves that multiple Swift buttons can open different RN views from the same bundle.

## iOS Dependency Setup

Add CocoaPods support for React Native:

- Root `Gemfile` pins CocoaPods and Xcodeproj versions compatible with modern Xcode projects.
- `Podfile` configures the `Fe` target and calls React Native's pod helpers from `node_modules/react-native`.
- `pod install` generates `Fe.xcworkspace`.

After CocoaPods integration, the app should be opened and built through `Fe.xcworkspace` rather than `Fe.xcodeproj`.

The Xcode target should set `ENABLE_USER_SCRIPT_SANDBOXING = NO`, because React Native's iOS integration requires this for its scripts and Hermes handling.

## Debug And Release Behavior

Debug builds load JavaScript from Metro:

- `npm start` starts Metro at the repository root.
- The native app loads the `index` bundle from the dev server.

Release builds load the bundled JavaScript from the app bundle:

- Add the React Native "Bundle React Native code and images" build phase.
- The script uses React Native's `with-environment.sh` and `react-native-xcode.sh`.

## Testing And Verification

Verification should cover:

- JavaScript dependencies install with npm.
- CocoaPods install successfully.
- The workspace builds for an iOS simulator.
- Metro starts successfully.
- The native SwiftUI screen can open at least three different RN pages.
- Each opened RN page shows route-specific content, confirming initial props flow from Swift to React Native.

If automated UI tests are not present, the first implementation should still include build-level verification and a manual run checklist.

## Out Of Scope

This integration does not include:

- Android support.
- A JavaScript navigation library.
- Deep linking.
- Native-to-JavaScript event emitters.
- JavaScript-to-native modules.
- Production app content beyond minimal page examples.

These can be added after the brownfield RN boundary is working.
